この資料で扱うこと

AIを使える環境から、AIを使って仕事を完了でき、その経験で次の仕事が改善される組織へ進むための構想書です。開発プロセス、共通基盤、人材・役割、統制、展開・改善を一続きで設計します。開発以外の業務も同じ考え方で扱い、まず既存のGemini利用から広げます。

開発者、チーム責任者、基盤・推進担当、IT・セキュリティ担当、投資判断者が、共通の全体像を持ち、着手する仕事を決めることを目的としています。

01 / CONTEXT

現在地と、組織で取り組む理由

出発点は「未導入」ではありません。すでにある契約・実践・知識を、組織で使える状態へつなぎます。

領域確認できていること次に整えること
開発ツール現状会社契約のGitHub Copilotを各個人が利用。一部でClaude Codeも利用。利用モード・端末・認証・権限の把握。チームで再現できる設定と仕事の手順。
開発以外のAI活用現状Google Workspaceの契約があり、Geminiを利用。契約内で使える機能を確認し、会議後の整理、調査、文書作成などの業務手順へ組み込む。
エージェント現状現在使っているエージェントは、GitHub CopilotとClaude Code。両者を共通の課題・テストで評価し、得意な作業と許可する実行範囲を決める。
設計情報現状設計書のMarkdown化を進めている部門がある。書式だけでなく、正本、更新責任、コードとの対応、AIが必要部分を探せる導線を整える。
スキル・ノウハウ現状スキルをそれぞれで作っている。全体統制はできていない。個人の実験を生かしながら、共有候補の評価、配布、バージョン管理、保守担当を設ける。

すでにある強み

利用を始める入口があり、先行実践者もいます。新規製品の調達や全社の情報移行を待たずに、実際の仕事を通じた標準づくりを始められます。

個人利用のままでは残る課題

設定・知識・使い方を各自が組み立て、失敗の対策も分散します。作成者の異動でスキルが止まる、実装は速くてもレビューが詰まる、といった問題は、チームと組織の設計課題です。

外部知見：DORAは、AI利用の成果を支える基盤を「開発者向けの社内プロダクト」と捉え、代表的な仕事を改善する最小構成から育てることを推奨しています。[2] DORA
計画前提従来資料の「約100名・10チーム・50システム」を、展開規模の仮置きに使います。現在の人数・システム一覧、各ツールの契約プラン、Claude Codeの認証・課金方法、既存CI・テスト・端末管理の実態は着手時に確認します。未確認の構成を「整備済み」とは扱いません。
02 / TARGET EXPERIENCE

目指すのは、現場の仕事が変わること

現時点の目標は、AIを特別な試行ではなく、品質と責任を伴う日常の仕事の進め方にすることです。

目指す姿

各チームが、必要な知識と検証手段を備えた環境でAIに仕事を任せ、人が目的・重要な判断・成果の受入れに責任を持つ。そこで得た改善が、次の仕事と他チームの標準に継続的に反映される。

例えば、担当者が小さな仕様変更に取り組む一日

01

迷わず始められる

承認済みアカウントで利用し、対象リポジトリの開始手順を実行。担当システムの注意点と、使えるスキルが分かる。

現場の変化：環境設定と使い方の探索を毎回繰り返さない
02

意図を共有して任せる

変更目的、受入条件、触れてはいけない範囲を示す。AIが関連コード・設計を調べ、根拠付きの変更案を出す。

現場の変化：単発の質問から、成果を求める依頼へ
03

実装と検証がつながる

AIが実装・テストを反復。実際の検証結果と未確認点を残し、失敗時は決めた条件で人へ戻す。

現場の変化：「できました」の返答だけで完了しない
04

レビューで判断できる

差分、判断理由、テスト結果、残るリスクがPRにそろう。人は要求と設計・影響を確認し、責任を持って受け入れる。

現場の変化：確認材料を探す時間を減らす
05

仕事の完了が知識になる

関連する設計・手順・運用情報も更新。重要な判断を、次の担当者とAIが参照できる場所に残す。

現場の変化：コードだけ進み、説明が古くなる状態を減らす
06

次の仕事が少し良くなる

詰まった理由を記録。チームがテストやスキルを改善し、有効な変更は共通版として他チームにも届く。

現場の変化：同じ失敗の再発を、個人の注意力に頼らない

到達したかは、行動と成果で確かめる

観点到達状態確認方法
使える先行実践者以外の担当者も、標準手順で対象業務を完了できる。新規参加者による実作業、初回完了までの障害・支援時間
役立つ確認・手戻りを含めた仕事全体が改善し、空いた力を顧客価値や負債解消に回せる。総作業時間、待ち時間、受入品質、再投資した成果
任せられる利用データ・実行権限・人の確認点・停止方法が明確で、実際に機能する。権限逸脱テスト、PR・実行記録、停止・復旧訓練
育つ現場で見つかった改善が、評価を経て標準に反映され、再発が減る。改善記録とリリースの対応、同種失敗率、別チームでの再現
変えない軸と、変える実装を分ける。「業務価値・品質・人の責任・学習する仕組み」は維持します。モデル、製品、スキル形式、接続方式、任せる仕事の範囲は、評価結果に応じて変更します。全システムを同じ日程で完全自律化することを、達成条件にはしません。
03 / BLUEPRINT

全体構想：現場・共通基盤・組織運営を一体にする

「基盤」はサーバーやAI製品だけではありません。仕事の手順、再利用資産、相談できる人、改善の運営までを含みます。

共通化するもの

利用の基本ルール、設定の配布方法、開始手順、検証・記録の形式、標準スキル、問い合わせ窓口。

現場で変えるもの

業務の受入条件、設計・品質基準、ドメイン知識、個別のテスト、担当システムに合う作業手順。

評価して選び直すもの

モデルとエージェント、共通基盤の実装方式、接続製品、任せる作業の範囲、投資する対象業務。

04 / WORKFLOW

AI駆動開発を、コード生成の外まで広げる

AI駆動開発を「目的に沿ってAIが調査・実装・検証を反復し、人が適切な判断と受入れを担う開発」と定義します。

仕事の段階AIに担わせること人が担うこと残す成果物・根拠
1. 課題・要求問い合わせや仕様の整理、論点・不足情報・影響範囲の候補出し。なぜ行うか、何を変えないか、顧客価値、受入条件を決める。チケット／作業カード。目的、対象外、具体的な受入例。
2. 調査・設計コード・仕様・過去判断の検索、変更案とテスト観点の作成。業務ルール、非機能、権限、互換性、設計上のトレードオフを判断。根拠リンク付き変更計画。大きな判断は設計・ADRに残す。
3. 実装・テスト小さな単位で修正し、ビルド・テストを実行。失敗に基づいて修正。曖昧な仕様、作業範囲の拡大、予想外の失敗に対応する。差分、実行コマンドと結果、失敗・未確認事項。
4. レビュー自己チェック、変更説明、レビュー観点とリスクの提示。要求充足、設計、重要コード、テストの妥当性を確認し、受け入れる。PR、CI結果、レビュー記録。AIレビューだけを承認としない。
5. リリースリリースノート、確認手順、ロールバック案の作成。適用判断、段階リリース、必要な承認。本番操作は別の実行権限で管理。変更記録、適用結果、ロールバック手順。
6. 保守・学習ログの整理、障害の一次調査、手順・テスト・設計の更新案。事実と仮説を分け、根本原因、恒久対応、次の改善を決める。障害記録、評価ケース、修正された標準資産。
作業の大きさに合わせて軽くする。小さな修正は、チケットに目的・受入条件・検証方法があれば開始できます。影響の大きい変更だけ設計資料やADRを追加します。全工程を毎回やり直す直線的な手順ではなく、調査・実装・テストを往復します。
公式の実践知：Anthropicの2026年8月のSDLCガイドは、実装が速くなると計画・テスト・レビューなどへ制約が移ること、各段階の成果物で文脈を引き継ぐことを扱っています。本資料では、作業規模に応じた軽量化と、人による受入れを組み合わせます。[3] Anthropic

開発以外も、同じ「目的 → 根拠 → 作成 → 確認 → 更新」で進める

最初の業務例：会議から実行へ

Geminiで試す：利用可能な議事情報・関連文書から、決定事項、未決事項、担当・期限の候補を整理。担当者が出典と意味を確認し、既存のタスク管理へ登録します。

用意するもの：入力してよい情報の例、出力ひな形、原文リンクの付け方、確認担当、測定する「会議後の整理＋確認」時間。録音・外部共有のルールも確認します。

チケットへの自動登録や外部送信は、接続・権限を別途整えてから。まず既存機能内で手動確認します。

段階を分ける業務

障害対応：読み取り中心の証拠収集・時系列整理から開始。復旧判断と本番変更は運用責任者が担当します。

データ分析：承認済みデータとクエリ範囲で集計・説明を支援。数値・母集団・意味は業務側が検証します。

顧客向け機能：AIを製品に組み込む場合は別のプロダクト開発として扱い、顧客影響、品質評価、利用規約、稼働監視を追加します。

05 / CAPABILITY BACKLOG

何を整備するか：9つの能力と具体的な成果物

大きな基盤を一度に完成させるのではなく、対象の仕事が一巡するために必要な最小セットをつくります。

最初の90日で、先行対象に提供するもの。担当名は09章で定義。
能力・主担当整備する成果物90日以内の提供範囲使えると判断する条件
① 利用環境
IT＋基盤担当		承認済みの「製品×利用モード×認証×データ範囲」一覧。標準設定、利用開始・退職／異動時の手順。現行Copilot・Claude Code・Geminiの棚卸し。先行利用端末で設定を配布・検証。想定メンバーが利用開始でき、権限のない操作を止められ、解除・停止も実行できる。
② 文脈・知識
チーム責任者		システムの入口文書、用語、構成、重要ルール、設計判断、正本へのリンク。更新責任・確認日。3〜5リポジトリの「よく変更する領域」に絞る。全面Markdown化は着手条件にしない。別の担当者とAIが必要情報を探せ、誤った・古い情報を指摘して更新できる。
③ 実行・検証
基盤＋チームQA		再現できる起動・ビルド・テスト手順、テストデータ、CI、PR保護、停止・復旧手順。対象作業の正常・異常・回帰テスト。エージェントの編集は分離された作業場所で実施。標準環境で再実行できる。AIの自己申告ではなく、実際の結果で受入可否を判断できる。
④ スキル・手順
基盤＋各資産所有者		共有カタログ、標準スキル、利用例、評価セット、版番号、所有者、変更履歴、配布・撤回手順。候補を棚卸しし、まず3つ程度を標準化。共通Gitと既存の配布機能から開始。作成者以外が使って同種の成果を出せ、どの版を使ったか分かり、前の版へ戻せる。
⑤ 情報への接続
基盤＋データ所有者		データ／接続カタログ、目的別の権限、認証、読み取り・書き込みの区分、接続試験。最も必要な読み取り接続を1件、必要性が確認できた場合に実装。既存連携で足りればMCPは増やさない。未許可の情報を取得できない。取得元・時点が分かり、接続を個別に止められる。
⑥ 評価・可視化
評価担当＋推進責任者		代表課題、失敗ケース、採点基準、導入前の値、実行記録、業務別の成果・費用表。2つの開発チームと1つの業務手順で測定。最初は既存メトリクス＋小さな記録表。採用・改善・中止を判断できる。未取得データや測定対象外も分かる。
⑦ 定着・支援
現場支援担当＋管理職		実務ハンズオン、能力別の育成内容、相談窓口、伴走計画、よくある詰まりへの解決手順。先行2チームに伴走し、次のチームへ引継ぎ。学習時間と既存業務の調整をセットで確保。先行実践者に頼らず仕事が完了し、問い合わせから標準の改善につながる。
⑧ 方針・責任
部門責任者＋IT・セキュリティ		利用範囲、データ分類、承認点、成果の責任、例外・変更・事故時の手順。委託先にも適用する条件。「通常利用」「新しい接続・実行」「高リスク」の3経路を文書と設定に落とす。通常利用で毎回の中央審査が不要。例外の判断者と期限、現場の相談先が明確。
⑨ 継続運用
基盤＋運用責任者		資産台帳、リリース手順、通知、稼働・費用上限、障害対応、廃止・移行手順。標準資産の更新運用を開始。無人の定期実行は限定領域での設計・試験までを基本とする。担当者不在でも止められる。障害時に業務へ戻れる。保守の時間・費用を見込んでいる。
着手順：対象業務と責任者を決め、①〜④・⑥〜⑧を小さく同時に整えて仕事を一巡させます。⑤は必要な情報が足りないときに追加。⑨の版管理は初日から、定期自動実行は検証・復旧が整ってから進めます。
06 / REPOSITORY STANDARD

開発の標準セット：文脈・実行・検証をそろえる

Markdownの設計書とスキルを、実際にビルド・テストできる環境につなぎます。この組合せを、本資料では「開発の標準セット」と呼びます。

repository/
├─ README.md             # 開始・実行・検証の入口
├─ docs/
│  ├─ domain.md          # 用語・重要な業務ルール
│  ├─ architecture.md    # 構成・依存・重要な制約
│  ├─ decisions/         # 設計判断と理由
│  └─ source-map.md      # 正本・所有者への導線
├─ ai/
│  ├─ common/            # ツール共通の指示の原稿
│  └─ asset-manifest.*   # 採用資産・版・対応環境
├─ .github/
│  ├─ copilot-instructions.md
│  ├─ skills/            # 検証した配布形式の一例
│  ├─ workflows/         # CIと受入れの検査
│  └─ PULL_REQUEST_TEMPLATE.md
├─ CLAUDE.md             # Claude Code向け入口
├─ .claude/skills/       # 必要なら別形式に配布
├─ scripts/              # 起動・検証の実行手順
└─ tests/                # 正常・異常・回帰の検証

ひな形に含める、最低限の5点

  1. 何のシステムか：目的、責任者、重要な業務制約。
  2. どう動かすか：必要環境、依存、起動・テストの確実な手順。
  3. どう依頼するか：目的・受入条件・変更範囲・中断条件。
  4. どう確かめるか：既存テスト、独立した受入例、レビュー観点。
  5. どう戻すか：差分管理、既知の正常状態、設定・資産の版。
このツリーは構成案です。ai/以下を製品が自動読込するとは限りません。製品ごとの入口から参照・生成し、対象のIDE／CLIで読込を試験します。同じ内容を複数箇所で手編集しません。既存のCI製品・設計管理方式に合わせて置き換えます。

「AIへの指示」と「実行を制約する仕組み」を分ける

目的手段扱い
意図・作法を伝えるCopilot用指示、CLAUDE.md、スキル、作業カード。理解・行動を助けるもの。指示文だけで秘密情報保護や承認を保証しない。
変更の品質を確かめるビルド、型・静的検査、業務テスト、セキュリティ検査、必須CI。実行可能な検査にする。テストの削除・弱体化やCI設定の変更もレビュー対象。

GitHubの公式資料は、指示・スキル・フックなどの対応がIDE／利用面ごとに異なることを示しています。Claude Codeにも共通仕様への独自拡張があります。共通の原稿と製品別の薄い設定を分け、実機で互換性を確かめます。[13] GitHub [17] Anthropic

既存システムは、使える範囲から段階的に整備する

A. 理解・調査に使う

信頼できる入口情報と参照範囲を用意。設計の復元案は、現行コード・挙動・有識者で確認。AIの推測を確定仕様にしません。

B. 変更・PRまで任せる

再現できる環境、対象範囲のテスト、必須レビュー、切戻しを用意。変更頻度が高く、検証可能な領域から着手します。

C. 定期実行へ広げる

Bに加え、サービス用ID、隔離実行、時間・費用・件数上限、通知、停止、再実行・復旧を整備。まず提案PRまでに限定します。

これはシステムの「優劣」ではなく、作業別の利用準備区分です。テストが薄いシステムでは挙動を固定するテストから整備し、重要な未検証領域は人の作業として残します。全50システムの文書化完了を待つ必要はありません。

測定の設計

  1. 同種の課題を選び、導入前の時間と品質を記録する。
  2. 同じ受入基準を使い、経験、難易度、対象領域、使用版を残す。

  5. 少数事例の改善を全社に外挿しない。案件構成の違いも併記する。

初期目標の置き方

例えば「反復する変更の総作業時間を10%改善し、受入品質を悪化させない」を仮の検証目標にします。10%は効果予測ではなく、投資判断の仮置きです。

着手時に、何をもって品質維持とするか、何件・どの種類の仕事を見るかを決めます。件数が少ない場合は、傾向として扱い拡大前に追加検証します。

重大な事故が起きなかったことだけでは安全を証明できません。権限・停止・復旧の意図的な試験も実施します。

投資は、費用と「生まれた余力の使い道」をセットで考える

月次の投資額 ＝ ライセンス固定費 ＋ 従量利用費 ＋ 実行・保存などの基盤費 ＋ 共通基盤の整備・保守・支援工数 ＋ 現場の追加学習・確認工数。

創出した余力は、総作業時間の差を対象件数で確認します。待ち時間の短縮と人の作業時間の削減は別に扱います。案件差・他の改善の影響を検討し、同じ時間を二重計上しません。

余力の再投資先は、顧客課題、機能改善、テスト不足、老朽化、障害予防などから責任者が決めます。工数換算の便益は、実際の支出削減や売上増とは分けて報告します。
