AI SRE — 障害対応の調査・整理・報告をAIへ

アラート発火と同時に調査を開始し、数分で「状況＋原因仮説＋類似事例」を提示。人間は判断に集中する。対応記録は③に自動蓄積され、対応するほど賢くなる。

1. 何を解決するか

深夜の30分
オンコール担当がログ・メトリクス・デプロイ履歴をかき集める初動時間
属人
「あの人しか直せない」— 50システムの障害知識が有識者依存
30〜70%
AI SRE導入企業のMTTR削減実績レンジ
Rootly等[1]

2. アーキテクチャと段階導入

2-1. 障害発生時の流れ（Step 1: 一次調査アシスト）

アラート発火CloudWatch alarm → EventBridge
→
調査エージェント起動④経由で メトリクス／ログ／直近デプロイ／構成変更 を横断照会（読み取り専用）
→
類似事例検索③のナレッジから過去の同型障害・ランブックを取得
→
5分以内に投稿障害チャネルへ「状況サマリ＋原因仮説（確度つき）＋類似事例＋次に見るべき場所」
→
人間が判断仮説を検証し対処。エージェントは追加調査の指示を受け続ける

2-2. 3段階の導入と昇格基準

段階できること次へ進む基準
Step 1
一次調査		読み取り専用の調査・仮説提示・類似事例提示原因仮説の的中率60%以上を3ヶ月継続（対応者が投稿に「役立った/外れた」をワンクリック記録）
Step 2
報告自動化		対応ログからタイムライン・報告書ドラフト・再発防止案を生成 → 人間レビューで確定 → ③へ自動蓄積報告書の修正率が軽微（構成の手直し不要）になること
Step 3
リカバリ支援		ランブック化された定型対処（再起動・切り戻し・スケール変更）を人間承認付きで実行対象操作はdenylist外・ランブック整備済みに限定。Phase 3で開始

2-3. 実装の2案（Phase 1末に比較評価 — 検討項目C-4）

案A: AWS DevOps Agent（第一候補）案B: 内製（Claude Code＋MCP）
強み提供システムがAWS上のためテレメトリ直結。2026年3月GA、マネージド。6月からスケジュール実行のSREボットとMCP／A2Aツール接続に対応し、夜間一次調査の定期実行が製品機能で成立する[2]②④の資産を流用。ランブック・報告書テンプレを自社流に作り込める。ヘッドレス実行＋MCPで構成
弱みカスタマイズの自由度、非AWS要素（Databricks等）の扱い構築・保守の工数。停止条件等の作り込み責任
評価方法同一の過去障害10件を両者に再現調査させ、仮説精度・調査時間・コストを比較（③に記録が溜まってから実施）

3. 運用

導入時
対象は障害頻度の高い上位5システムから（ハーネス②・設計書③整備済みが条件 — 文脈がないと調査精度が出ない）
障害のたび
対応者が「役立った/外れた」を記録（的中率KPIの源泉）。確定した報告書は③へ自動蓄積
月次
外れた仮説のレビュー → 調査手順スキル（ops-incidentプラグイン①）を改善。アラートのノイズ源も棚卸し
四半期
対象システムの拡大判断。Step昇格の判定
Human-in-the-Loopの線引き（L1基準） 本番への書き込み操作は常に人間承認付き（Step 3でも変わらない）。エージェントの提案と実行ログはすべて監査対象（④）。 「AIが勝手に本番を直す」は目指さない — 目指すのは人間の判断時間を最大化すること。

4. KPIと計測方法

指標取得方法目安
MTTR（平均復旧時間）インシデント管理の起票→解決時刻（⑤と共通。AI時代に最も歪みにくい指標）−30%〜
一次調査カバー率アラートのうちエージェント調査が走った割合対象システムで95%+
原因仮説の的中率対応者のワンクリック記録（役立った/外れた）60%でStep 2へ
報告書作成時間障害クローズ→報告書確定の時間−80%
調査あたりコスト④⑤のログ（¥/障害調査）人件費換算と比較提示

5. 事例と落とし穴

事例 AWS DevOps Agent／Azure SRE Agent 2026年3月GA（テレメトリ・コード・デプロイ履歴の横断分析）。AWS DevOps Agentは2026年6月にスケジュールSREボットとMCP／A2A接続を追加[2]。 Rootly等の専業はアラート発火と同時に調査を開始し数分で根本原因候補を提示、MTTR 30〜70%削減の実績[1]。 AIOpsは2026年に「異常検知」から「自律的エージェント運用」へ移行[3]。
落とし穴（反面教師） 自動化バイアス（もっともらしい誤診断を人間が鵜呑みにする — 仮説には必ず確度と根拠リンクを付けさせ、的中率を公開する）／ アラート洪水への直結（ノイズアラートのたびにエージェントが走るとコストが溶ける。重複排除・重要度フィルタを前段に）／ 文脈なしで対象拡大（②③未整備のシステムでは精度が出ず信頼を失う。整備済みから広げる）／ 書き込み権限の先行付与（Step 1は読み取り専用を厳守）。
