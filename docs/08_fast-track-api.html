Fast-Trackレーンと共通APIゲートウェイ — 整備を待たせない受け皿

「業務でLLM APIを使いたい」という現在進行形の要望を止めずに、ガバナンスの中に乗せる。原則は「禁止でも放任でもなく、舗装された道を最速で提供する」。

1. 何を解決するか — 「整備待ちの死」と「野良APIの氾濫」の二択を壊す

基盤整備には時間がかかる。その間に現場の要望を止めれば、事業機会と信頼を失い、世の中の変化にも置いていかれる。 逆に自由に使わせれば、契約条件（学習利用）・データ分類・コストが統制不能になり、後から回収するコストは膨大になる。

整備待ち
「ガバナンスができるまで待って」→ 現場は待たない。シャドーAI化するだけ
放任
個人契約のAPIキーが業務システムに混入 → 契約・監査・コストが統制不能
舗装路
正規ルートを「最速・最も楽な道」にする — プラットフォームエンジニアリングのPaved Road原則[1]
設計思想 統制は「審査を重くする」ことではなく「正規の道を野良より速く・楽にする」ことで実現する。 申請が面倒だから野良に流れる — なら申請を3問にし、低リスクは即日で通す。正規ルートには最初から計測（⑤）と監査（④）が組み込まれているので、使われるほどガバナンスが強くなる。

2. Fast-Trackレーン — 要望を止めない受け入れプロセス

1. 申請（3問だけ）①何に使うか ②扱うデータの分類 ③出力を人が確認してから使うか
→
2. 自動トリアージ社外秘以下×人の確認あり×承認済みモデル → 低リスク: 即日〜翌日承認。それ以外は週次審査（SLA 5営業日）
→
3. キー払い出し共通ゲートウェイの仮想キー（チーム・用途タグ、予算上限、レート制限つき）
→
4. 暫定利用（90日）利用ログ・コストは自動で⑤へ。ガードレール5点（§4）の範囲で自由に使う
→
5. 90日レビュー実績を見て 本則化／改善して継続／停止 を判定。得られた知見は①③へ還元

※ ポイントは「暫定承認＋期限付きレビュー」。完璧な事前審査を諦める代わりに、計測に基づく事後判定を制度化する

「様々な要望」への一般化 — インテーク(受付)の一本化

要望の分類扱い例
A. 既存の舗装路に乗るFast-Trackで即提供（このページの仕組み）API利用、MCPツールの暫定登録（読み取り専用から）、承認済みツールの追加シート、Tier 1エージェント
B. 新しい道の舗装が必要暫定手段を提示しつつ、四半期の舗装計画（ロードマップ）に反映新ツール導入、新しい接続先、新ユースケース類型
C. 例外（リスク高）個別審査（セキュリティ担当と合議）。断る場合も代替案とセットで返す機密データの投入、顧客向け自動応答、本番書き込み
要望はノイズではなく「需要側シグナル」 ⑦フロンティアウォッチが「技術の供給側」の入力なら、インテークは「現場の需要側」の入力。 月次で要望の傾向を集計し、舗装の優先順位（ロードマップ）に反映する。整備計画は固定物ではなく、この2つの入力で回る計画ループになる。

3. 技術の受け皿 — 共通LLM APIゲートウェイ

④MCPゲートウェイが「エージェント→社内システム」の統制点なら、⑧は「アプリ／業務→LLMモデル」の統制点。対で「2つの関所」になる。

利用側業務システム／社内ツール／スクリプト／エージェント
→
共通ゲートウェイ1エンドポイント（OpenAI互換API）。仮想キーで認証
→
統制予算上限・レート制限・ガードレール・モデル許可リスト（no-training契約のみ）
→
モデルBedrock(Claude)／Gemini／その他承認済みプロバイダ
→
記録全呼び出しのログ・コストをチーム/用途別に⑤へ自動集約

向く用途データ利活用API・RAG・業務エージェント（本番含む）、社内ツール、分析系マルチプロバイダの社内共通API（E-1で不足が出た場合の控え）データに依存しない純モデル呼び出しを、AWS本番システムの同期パスに最少ホップで組み込む場合

アーキテクチャから先に判断できること（検証を待たない一次判定）

向き不向きの大勢は、提供方法とアーキテクチャからPoC前に判定できる。E-1・E-3はいずれも本番システムに組み込める本番グレードの基盤であり、分かれ目は次の7観点にある。

本番／社内のワークロード分離

クリティカルパス依存
依存するクラウドサービス自体の障害への巻き込まれ範囲		△ 可用性チェーンにDatabricksが加わる◎ AWSのみ
設計原則: 共通にするのは「仕組み」、分離するのは「実行資源」 「共通ゲートウェイ」とは、ルール・キー払い出し・可視化・監査という管理の仕組みを1つにすることであり、全利用を1本の実行資源に乗せることではない。 本番サービス利用と社内利用は、キー払い出しの時点で別レーンに分け、E-1ならエンドポイント（＋必要ならワークスペース）、E-3ならAWSアカウントを分けて紐づける。 これにより社内利用がどれだけ暴れても、本番サービスの容量・クォータ・可用性には届かない。ガードレール5点と⑤の可視化は両レーンに同一に適用される。
一次判定ルール: 原則E-1、例外条件に該当したらE-3 データに依存しない純粋なLLM利用でも、E-1は外部モデルエンドポイントを設定で立てるだけ（OpenAI互換で呼べる）で、レート制限・権限・コスト配賦・ログが最初から付く。 「簡単に作れて統制も付く」という舗装路の要件を最も満たすため、データ利用の有無を問わずE-1を既定とする。
E-3（Bedrock直）に切り替えるのは、次の例外条件に該当する場合: ①閉域要件が厳しく、外部モデルEPのPrivateLink未GAリージョンである ②ミリ秒級の同期レイテンシ要件がある ③AWS IAMでの権限統一が必須の基幹系である ④Databricks障害時にも止められない可用性分離要件がある。
PoCで測るのは方向ではなく数値: 実測レイテンシ（P50/P99）、負荷時のスループットとクォータ挙動、運用コスト（DBU・転送）、障害時フォールバック。第1号案件で「数字の裏取り」だけを行う。

APIだけではない — MCP・エージェントも同じ受け皿に乗せる

現場から出る要望は「APIを呼びたい」だけでなく「社内データ・ツールをMCPとして提供したい／使いたい」「エージェントを作りたい」を含む。 いずれも論点は同じ — どこで実装するか（一次判定）と、整備を待てないケースの受け皿（Fast-Track）。3類型で整理する。

提供物実装の置き場所（一次判定）Fast-Trackの扱い
API
モデル呼び出し		 原則E-1（Unity AI GW）、例外条件でE-3（上記ルール） 本ページの仕組みそのまま（仮想キー・90日レビュー）
MCP
ツール・データの提供		 データ系ツール（テーブル・Genie・Vector Search・UC関数）→ Databricksのmanaged MCPサーバー（設定で提供でき、Unity Catalog権限がそのまま効く[2]）。 社内API・Lambda系ツール → AgentCore GatewayでMCP化（④の実装候補と同一）。特殊要件のみ自作（Databricks Apps／ECS）。 どの経路でも必ず④の承認済みレジストリに登録して全エージェントから発見可能にする 暫定登録レーンを用意: 読み取り専用スコープ＋利用ログ必須で即日登録 → 90日レビューで本登録。レジストリ外の野良MCPは禁止（L1ルール）のまま、正規登録を速くすることで両立する
エージェント
構築・実行		 業務・データ系 → Agent Bricks（ガバナンス・評価込み[2]）。開発系 → Claude Code＋②ハーネス。実行環境はActions／AgentCore Runtime（検討項目D-3） Tier 1（報告のみ・読み取り専用）は Fast-Track対象。書き込み・自律実行を伴うものは例外審査（分類C）

この3類型はいずれも「⑧の受付（インテーク）→④⑤の統制点に自動接続」という同じ配管に乗る。受付を分けないことで、現場は「何を作りたいか」だけ言えばよく、実装の置き場所はAI推進チームが一次判定表で即答できる。

ロードマップへの組み込み — 前倒しで作る

⑧はPhase 1完成を待たない。Phase 0（アセスメント期間中）に最小構成で稼働開始する: Week 1-2 = 申請フォーム＋ガードレール5点の文書化、Week 3-4 = ゲートウェイPoC＋第1号案件のキー払い出し。 現在出ているAPI要望をそのまま第1号（灯台案件）にすることで、「整備が現場の役に立つ」最初の証拠を作る。

4. ガードレール — 暫定利用でも譲らない5点（L1ルール）

① 承認済みモデルのみno-training（学習不使用）契約が確認できたモデル・エンドポイントだけをゲートウェイの許可リストに載せる。個人契約キーの業務利用は禁止
② データ分類の遵守投入可否はL1のデータ分類マトリクスに従う。機密データはFast-Track対象外（例外審査C行き）
③ キーは共通ゲートウェイから仮想キー（チーム・用途タグ、予算上限、レート制限、有効期限90日）。生キーの直接配布はしない
④ ログと監査全呼び出しを記録し⑤に集約。コストはチーム・用途別に自動帰属（D-5の監査要件と共通）
⑤ 人の確認基準顧客向け出力・本番反映はHuman-in-the-Loop必須（L1既定と同一）。全自動化はFast-Trackの対象外
「止めない」と「何でも通す」は違う Fast-Trackが速いのは、ガードレールの内側だけ。5点の外に出る要望はC（例外審査）に回り、そこは従来通り慎重に判断する。 速さの源泉は「審査を省く」ことではなく「リスクの低い大多数を仕組みで即決する」こと。

6. 落とし穴

落とし穴（反面教師） Fast-Trackの審査が肥大化する（3問が10問になった時点で野良に負ける。質問を増やしたくなったら分類C行きの条件を明確化する方が先）／ 暫定のまま放置（90日レビューを飛ばすと「暫定」が実質無期限になり統制が空洞化。レビュー日はキー有効期限で強制）／ ゲートウェイの単一障害点化（本番組込み用途はSLA・フォールバック設計を先に確認。だからE-3併用の選択肢を残す）／ 統制側の勝利宣言（経由率が上がっても、リードタイムが伸びたら失敗。速度と統制の両方をKPIにする）。
