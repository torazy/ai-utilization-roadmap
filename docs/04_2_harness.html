標準ハーネステンプレート ＝ 実行される開発標準

エージェントが安全に・正しく・長時間働ける環境をリポジトリ内資産として定義する。文書標準と違い、エージェントが従うことで「自動的に実行される」標準。

1. なぜハーネスか — METRの警告から

0
ハーネスなしでAIを使った経験豊富な開発者は、むしろ遅くなった
METR実験（体感は+20%速いと誤認）[1]
−7.2%
AIコード比率+25ppごとに安定性指標が低下
DORA 2025[2]
反転可能
文脈供給＋機械的検証があれば速度と品質は両立する
OpenAI Codex/Anthropicの実践[3]

METR実験の遅延要因は「AIの出力が信頼できず、全行を目視確認・修正していた」こと。つまり問題はモデルではなく、文脈の供給不足と検証の人力依存。 ハーネスはこの2つを構造的に解決する — AGENTS.mdが文脈を常時供給し、CI不変条件と評価エージェントが検証を機械化する。

なぜ「ルールを書けば従う」が成立しないのか — LLMの構造的制約（公開研究）

ハーネスの各部品は思いつきではなく、LLMの測定済みの制約への対応になっている。「文書標準が守られない」のと同じ現象がAIにも構造的に起きる。

構造的制約根拠（実測・論文）ハーネス側の対応
コンテキストは長いほど劣化するChromaが18モデルで実測 — 上限のはるか手前から非線形に性能低下[6]AGENTS.mdは「1枚メモ＋リンク」構造。スキルの遅延ロード、フェーズ分割
指示を増やすほど個々の遵守率が下がるIFScale — 指示密度の上昇で遵守率が減衰。最高モデルでも500指示で68%[6]ルールを「書いて祈る」のをやめ、CI不変条件・Hookで機械的に強制する
自己申告は完了の証拠にならないSWE-bench等の評価設計思想（自己申告を排しテストのpass/failで判定）[6]完了条件をテスト・exit codeで定義（AGENTS.mdの「完了条件」＋評価エージェント）
バイアスは自覚されないAnthropic研究 — モデルは入力のヒントに影響されつつ、思考過程でそれに言及しない[6]生成と評価を別コンテキストに分離（計画/生成/評価のサブエージェント分離）
運用原則: 失敗の昇格ラダー 同じ失敗が2回起きたら、現在の段では防げていない証拠 — 1段上へ昇格させる: L0 口頭で指摘（セッションを跨がず消える）→ L1 AGENTS.mdに記載（確率的に守られる）→ L2 スクリプト検証（exit codeで判定、実行忘れはあり得る）→ L3 Hook／CIゲート（通過必須・物理的に再発不可能）。 L3まで上げた失敗は構造的に再発しない。「注意喚起で直そうとし続ける」のが最も高くつく。

2. 技術構成 — リポジトリに置く7点セット

作業指示書（AGENTS.md / CLAUDE.md）— 書きすぎない

# AGENTS.md（例: 決済システム）
## ビルド・テスト
- ビルド: `./gradlew build` ／ 単体テスト: `./gradlew test`
- 統合テストはCIのみ（ローカル実行禁止: 外部接続あり）

## 触ってよい領域 / いけない領域
- 変更可: src/main/java/com/x/payment/**
- 変更禁止: src/main/java/com/x/legacy/**（凍結中）、DBマイグレーション（人間が作成）

## 規約
- 例外は PaymentException 系に集約。ログは構造化ログ（logback、JSON）
- 詳細設計は docs/design/ を必ず参照（AIリバース生成済み）

## 完了条件
- `./gradlew check` パス ＋ 変更行のテストカバレッジ80%以上

コツ: ルールブックではなく「新人に渡す1枚メモ」。長すぎると読み飛ばされる（モデルも同じ）。詳細はスキル（①）と設計文書（③）に分離してリンクする。

CI不変条件 — エージェントの暴走を止める柵

不変条件実装例防ぐこと
アーキテクチャ境界ArchUnit ／ dependency-cruiserレイヤー違反・禁止依存の混入
フォーマット・命名Prettier ／ Checkstyle ／ ESLint（自動修正込み）スタイル指摘でレビューが埋まる
データ検証スキーマテスト ／ 契約テスト（Pact等）API/DB契約の暗黙破壊
セキュリティsecretスキャン ／ SAST ／ 依存脆弱性チェック秘密情報混入・脆弱コード
変更量ガード1PRの差分上限（例: 800行）を超えたら人間レビュー必須ラベル巨大PRの検証不能化

ポイント: 「レビューで人が指摘していたこと」を1つずつCIに移す。エージェントはCIが赤なら自分で直すので、柵は同時に自動修正ループの部品になる。

計画・生成・評価の分離（3エージェント構成）

# .claude/agents/（役割ごとに定義。Anthropicの3エージェントハーネス構成 [3]）
planner.md   # 計画: タスクを分解し docs/plan.md に書く。コードは書かない
builder.md   # 生成: plan.md に従い実装。テストを先に書く
checker.md   # 評価: 別コンテキストで差分・テスト・設計整合を審査
             #   → builderと同じ文脈を共有しない（甘い採点の防止）

Checkerの独立性が肝。「生成した本人が検証する」構成は形骸化する（→ ループ詳説の落とし穴参照）。

権限統制（managed settings — IT管理側で配布）

// managed-settings.json（AI推進チームが端末管理経由で配布 [4]）
{
  "permissions": {
    "allow": ["Bash(./gradlew *)", "Bash(git *)", "Read(**)", "Edit(src/**)"],
    "deny":  ["Bash(rm -rf *)", "Read(.env*)", "Read(**/secrets/**)",
              "WebFetch" /* 外部送信はMCPゲートウェイ経由のみ */]
  },
  "env": { "CLAUDE_CODE_USE_BEDROCK": "1" }  // モデル呼び出しをAWS域内に
}

組織強制（managed）と推奨初期値（Starter Kit）の2層で配る。開発者の工夫の余地は残しつつ、denyだけは上書き不可にする[4]。

再現可能環境と設計文書

  • devcontainer: ワンコマンドで人にもエージェントにも同一環境。worktree分離で複数タスク並行（ループの前提）
  • docs/design/: レガシーはAIリバース生成（legacy-docプラグイン→①）で整備。生成した設計書がそのままエージェントの常設コンテキストになるのがこの企画の要
  • 鮮度維持: 設計書とコードの差分をエージェントが夜間検出→更新PR起票（Phase 3、→③）

3. 運用 — 50システムへの展開

0. テンプレ取得template リポジトリから導入スクリプト実行（30分）
→
1. 文書リバースlegacy-docスキルで設計書・依存マップをAI生成（半日〜）
→
2. AGENTS.md生成ドラフトはAIが作成 → 有識者が30分で赤入れ
→
3. CI柵の設置不変条件セットから該当分を有効化
→
4. 試運転小タスク5本をエージェントに委任し成功率を確認 → 合格で「ハーネス整備済み」認定

※ 1システムあたり実働2〜3日（レガシー度により変動）。伴走連鎖でチャンピオンに移転

導入時
灯台チームの2〜3リポジトリでテンプレv1を検証 → フィードバックをv2に反映してから横展開
週次（自動）
テンプレ更新はマーケットプレイス（①）経由で各リポジトリに更新PRを自動起票 — 各チームはレビューして取込
月次
「ハーネス整備済み」リポジトリのタスク成功率をレビュー。失敗パターンをテンプレ改善に還元（⑦経由）

4. KPIと計測方法

指標取得方法目安
ハーネス整備済みリポジトリ数認定リスト（試運転合格制）— 企画全体の進捗KPI10 → 25 → 50
エージェントタスク成功率委任タスクのPR一発マージ率／手戻り回数（GitHub APIで自動集計）整備前後で比較
レビュー負荷PRあたりレビューコメント数の推移（機械的指摘がCIに移るほど減る）−30%
変更失敗率DORA指標（⑤で測定）— 悪化させないことが合格条件横ばい以上

5. 事例と落とし穴

事例 OpenAI Codexチーム: AGENTS.md＋再現環境＋CI不変条件の3点セット[3]。 Anthropic: 計画/生成/評価分離で長時間自律開発[3]。 国内: managed settings＋Starter Kitの企業配布パターン[4]。 メルカリ: 「Agent Spec駆動開発」を社内標準化してAI生成コード比率70%[5]。
落とし穴（反面教師） AGENTS.mdの肥大化（ルールブック化すると人もAIも読まない。1枚メモ＋リンク構造を守る）／ ハーネスなしの自律化（METRの-19%はこの状態[1]。試運転合格までは対話利用に限定）／ テンプレ更新の放置（自動PR起票で追従を仕組み化）／ 柵の過剰設置（開発が窮屈になったら柵を疑う。四半期で棚卸し）。
