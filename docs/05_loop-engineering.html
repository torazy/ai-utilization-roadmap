詳説 — Phase 3の中核手法

ループエンジニアリング詳説

「エージェントにプロンプトを与える自分自身を、システムで置き換える」（Addy Osmani, 2026年6月）。手動指示を廃し、指示の生成・送出・検証まで自動で回る系を設計する。

1. 定義と階層 — ハーネスとの関係

ハーネスが「1回の実行の装備」（モデル・ツール許可・文脈・検証）だとすれば、ループは「装備済みエージェントを反復制御する上位層」。 比喩では、ハーネス＝1試合の装備、ループ＝シーズン運営戦略[1]。したがってハーネス（②）の整備なしにループは成立しない — 本企画がPhase 1-2をハーネスに充てる理由。

2. 6つの構成要素[1] — 当社実装との対応

構成要素役割当社での実装（L2基盤との対応）
1. 自動化トリガーGitHubイベント・cronでループを起動GitHub Actions schedule／EventBridge（AWS構成）
2. 並列隔離git worktreeで複数エージェントの競合防止②devcontainer＋worktree。クラウド実行はAgentCore Runtime（セッション分離microVM）
3. 知識バンドルSKILL.mdでプロジェクト固有知識を供給①マーケットプレイスのスキル＋②AGENTS.md
4. 外部連携MCPで既存ツールに接続④MCPゲートウェイ経由（承認済みレジストリ）
5. 分業設計Maker-Checker分離で生成と検証を独立化②の計画/生成/評価サブエージェント＋CI不変条件
6. 状態保存セッションを超えた文脈保持CLAUDE.md／AgentCore Memory／Lakebase（③）
含意 6要素のうち5つはL2基盤①〜④がそのまま部品になる。ループはゼロから作るものではなく、Phase 1-2で作った基盤の「組み合わせ方」である。
実装部品の最新動向（2026年時点） Claude Code公式のAgent Teams（2026年2月・実験的機能）は、リーダー＋2〜16のチームメイトが共有タスクリストとメッセージングで協調する仕組みで、 「並列隔離＋分業設計」の公式実装候補になる[4]。研究面ではハーネス自体を外側ループで自動最適化するMeta-Harness（Stanford）が登場しており[4]、 ⑦フロンティアウォッチで両者の成熟を追跡する。

3. 安全装置 — 停止条件4点セット（必須）

ループ化したエージェントのトークン消費は通常チャットの5〜30倍に達し得る[1]。全ループに以下を必須実装とする（テンプレ化して②で配布）。

停止1 イテレーション上限

1タスクあたりの反復回数上限（例: 5回）。超えたら人間にエスカレーション

停止2 予算キャップ

ループ別の日次/月次トークン予算。⑤の上限アラートと連動し、超過で自動停止

停止3 無進展検出

同じ失敗の繰り返し・差分の振動を検出したら打ち切り（例: 同一テスト2回連続失敗）

停止4 サーキットブレーカー

失敗率が閾値を超えたらループ全体を停止し通知（例: 直近10実行の失敗5割）

4. 採点設計 — ループの品質は「回数」ではなく「止め方」で決まる

無限リトライ型のループ（原型: RALPH — 同じプロンプトをひたすら渡し直すシェル1行[4]）は粘り強いが、採点者が不在のため何周しても同じ失敗を繰り返す。 100周は努力の量であって品質の証明ではない。ループを品質に収束させるのは、仕事を「採点できる形」に翻訳し、続行判定を機械に渡す設計である。

4-1. 採点軸の作り方（3手順・3層）

1. あいまいな形容詞を書き出す「良い」「ちゃんとした」「読みやすい」— 人によって解釈が変わる言葉を拾う
→
2. 数えられる事実に翻訳「読みやすい」→「1文平均60字以下」、「速い」→「応答200ms以内」。機械が○×を出せる形に
→
3. 配点を振る観点ごとに配点し合計100点の物差しに。採点軸に書いたものだけが毎周チェックされる
層担当例
機械の○×スクリプト・テスト（CI相当。最も安く、ブレない）テスト全通過、文字数、フォーマット、exit code
観点つきLLM採点評価エージェント（観点を言語化して渡す）「構成が結論先行か」「訴求が刺さる1文があるか」
原則ドキュメント採点評価エージェント＋チームの原則集（②の資産）設計原則・レビュー基準への適合

機械の○×で済む部分はループを立てる必要がない（ただのCI）。品質ループが効くのは、○×に落ちない「全体の質」を観点化して収束させるところ。

4-2. 評価者の独立4原則（報酬ハッキング対策）

原則実装
① まっさらな別コンテキストで採点スキルの context: fork（公式機能[4]）で起動。生成側の会話・言い訳を一切見せない — 期待への迎合を構造的に断つ
② 採点基準を書き換えさせない評価基準ファイル・テストを permissions の deny で保護（「テストを直して通す」逃げ道を塞ぐ）
③ 絶対評価「前回より良いか」でなく毎回ゼロから依頼文と採点軸に照らす（スコアドリフト防止）
④ 報告でなく実物を確認生成側の「できました」は読まない。ファイルを開き、テストを自分で再実行してから採点

4-3. 続行判定は機械に渡す

「もう一周回すか」の判定に、AIも人も関与させない。AIに任せると期待に迎合して早く切り上げ、人に任せると10周目には根気が緩む。 「点数 ≥ 合格点か」「周回数 ≥ 上限か」は整数比較 — 応答終了のたびに自動実行される小さなスクリプト（Claude CodeならStop hook）に渡す。 状態（周回数・最新スコア・最良版）は会話でなくファイルに置くため、まっさらな頭で再開でき、コンテキスト劣化[4]の影響を受けない。

運用ダイヤルは2つだけ — 迷ったら採点軸を疑う 調整するのは合格点（threshold）と最大周回（max）のみ。コストは概ね「1周＝生成＋採点の2呼び出し」で読める。 「点は出るのに中身が良くならない」ときは、ダイヤルより先に採点軸の抜け穴（質と無関係な指標）を直す — 指標を目標にすると指標だけが最適化される（グッドハートの法則）。

5. 自律ティア — 段階的に権限を上げる[1]

Tier 1

報告のみ

分析・提案まで。実行は人間。
例: ⑦の収集レポート、③の差分検出通知

Phase 1〜2はここ。実績と信頼を積む

Tier 2

検証付き修正

変更をPRとして実装。マージは人間。
例: 夜間テスト補強・文書更新PR

Phase 3の主戦場。Checker＋CI柵が前提

Tier 3

無人実行

denylist外を完全自動化（自動マージ含む）。
例: フォーマット修正・依存パッチ版更新

Tier 2で誤り率が十分下がった対象のみ、範囲を明記して昇格

昇格基準の例: Tier 2で「人間レビューでの修正指摘ゼロ」が対象カテゴリで20回連続 → そのカテゴリのみTier 3へ。カテゴリ単位で昇格し、一括昇格はしない。

7. 組織側の運用 — 「理解の喪失」を防ぐ

毎朝（各チーム10分）
夜間ループの成果PRを確認・マージ。「AIの夜勤の検収」が朝会の新しい定例に
週次（チーム）
生成コードのウォークスルー枠（30分） — ループ任せで「何が動いているか分からない」状態になるのを防ぐ[1]。設計判断はADRとして③へ
月次（AI推進チーム）
全ループの成功率・コスト・停止発動履歴をレビュー（⑤）。不調ループは休止して原因分析
落とし穴（反面教師） コスト暴走（5〜30倍のトークン消費。停止条件4点なしのループは運用禁止をL1ルールに）／ 検証の形骸化（Maker と Checker が同一文脈だと甘い採点になる — 別システムプロンプト・別権限を必須に[1]）／ 理解の喪失（週次ウォークスルーを削った組織から壊れる）／ 一括Tier昇格（「もう大丈夫だろう」でまとめて無人化 → カテゴリ単位・実績基準を守る）。
