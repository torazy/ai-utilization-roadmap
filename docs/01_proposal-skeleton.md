# 企画書骨子: 生成AIによる開発プロセス変革

作成日: 2026-07-06 / ステータス: 骨子 v0.1（ディスカッション反映版）
前提資料: [00_discussion-base.md](00_discussion-base.md)

## 確定した前提

| 項目 | 内容 |
|---|---|
| 規模 | 部門全体 約100名 / 10チーム / 50システム |
| セキュリティ | 学習に利用されない環境であれば社外AIサービスにコード等を投入可。Claude利用は可 |
| 方針 | 最先端の活用水準を目指す（守りではなく攻めの企画） |
| 現状の成熟度 | 標準エージェントとの対話的な実装が中心。ハーネス構築の実践者は部門内に少数（企画者本人ら） |

## 1. 背景・課題（企画書の「なぜ今か」）

1. **バラバラ導入の限界**: 各部署が独自導入した結果、活用度に大きなばらつき。世界的にも同じ構図で、AIパイロットの88%は基盤（ガバナンス・環境・評価）の欠如で本番化に失敗している。
2. **AIは増幅器**: DORA 2025の結論。開発システムが未整備のままAIを足しても摩擦が増幅されるだけ。プラットフォームとイネーブルメントへの投資が価値実現の条件。
3. **技術進化の速度**: ハーネスエンジニアリング→ループエンジニアリングと、活用パラダイムが数ヶ月単位で進化。**個人の努力で追従するのは不可能になっており、「追従する仕組み」を組織として持つ必要がある**。
4. **レガシー50システムの機会**: 設計書が古い/ないシステム群は、AIリバースドキュメンテーションのROIが最も高い領域（先行事例: 文書化工数97%減）。
5. **コスト圧力**: Copilotの従量課金化（2026/6〜）等で、無秩序な導入はコスト爆発リスク。使い分けと測定が必須。

## 2. 目指す姿（12〜18ヶ月後の北極星）

- 全50システムに機械可読な設計ドキュメント＋ハーネス（AGENTS.md/CI不変条件）が整備され、**どのシステムでもエージェントが安全に作業できる**状態。
- 開発者は「エージェントと対話する人」から「**ループを設計し、エージェント群の成果を検収する人**」へ。夜間・イベント駆動の自律ループ（テスト補強、依存更新、ドキュメント鮮度維持）が常時稼働。
- 障害対応は一次調査・報告書ドラフトをAIが実施し、人間は判断に集中。MTTR 30%以上削減。
- ナレッジは蓄積も活用もAI: 障害記録・設計判断・レビュー知見が自動で構造化され、次のエージェント実行のコンテキストになる。
- 世の中の最新動向を自動収集・評価し、ハーネス/ガイドラインに反映する「**フロンティアウォッチループ**」が回っている。

## 3. 施策の全体像: 3層モデル（規模反映版）

### L1: ガバナンス・方針（共通で決める）
- **承認済みAIサービスリスト**: 学習オプトアウト（no-training）構成を条件に承認。
  - GitHub Copilot Business/Enterprise（学習不使用）— 全員
  - Claude（Team/Enterprise または API。学習不使用）— エージェント作業層
  - Gemini for Workspace（業務データ学習不使用）— 全社員・非開発業務
  - Databricks 上のモデルサービング — データ・ナレッジ系
- **データ分類×投入可否マトリクス**（企画書添付資料として作成）
- **Human-in-the-Loop基準**: 本番反映・顧客向け成果物は人間承認必須。AI事業者ガイドライン1.2版に準拠。
- **ツール使い分けマトリクス**（00資料 §2 参照）

### L2: 共通イネーブルメント基盤（CoEが構築・運用）

> 詳細設計（構成図・運用フロー・効果・事例注釈）は [02_L2-platform-detail.md](02_L2-platform-detail.md) を参照。
| # | 構成要素 | 初期スコープ（100人規模） |
|---|---|---|
| ① | 社内スキル/プラグイン・マーケットプレイス | 社内Gitリポジトリ1つ＋marketplace.json。企画者の既存ハーネス資産を初期コンテンツに |
| ② | 標準ハーネステンプレート | AGENTS.md/CLAUDE.md雛形、CI不変条件セット、devcontainer、レビュー/テストループ。**これが実質の新開発標準** |
| ③ | ナレッジ基盤 | 置き場は検討項目A（§7）。まず障害記録と設計書の自動蓄積パイプラインから |
| ④ | MCPゲートウェイ | 社内システム（チケット、監視、Wiki、DB）への統制された接続点 |
| ⑤ | コスト・効果ダッシュボード | 従量課金の可視化＋DX Core 4指標 |
| ⑥ | AI SRE | 障害一次調査・報告書ドラフト生成から開始 |
| ⑦ | フロンティアウォッチループ | 最新動向の自動収集・評価・反映（§4） |

### L3: 部門・チーム固有（各チームが所有）
- 各システムのハーネス（AGENTS.md等）、業務固有スキル、業務ナレッジ。
- チャンピオンが整備を主導。良いものはCoEが吸い上げて共通化（3ヶ月サイクルのレビュー）。

## 4. 最先端引き上げ戦略（本企画の差別化ポイント）

課題: 部門の現在地は「対話的なエージェント利用」。最先端（ハーネス→ループ）との差は大きく、かつ最先端自体が動き続ける。**「人を教育して追いつかせる」だけでは構造的に不可能**。

### 戦略の原則: 「型に乗せる」×「追従を仕組み化する」

**(1) 標準ハーネスで「使うだけで最先端の型に乗る」状態を作る**
- 最先端の実践（計画/生成/評価の分離、CI不変条件、スキル分割）をハーネステンプレートに焼き込み、リポジトリに配布する。
- 開発者はテンプレートに従って作業するだけで、最先端のプラクティスを「実行」することになる。教育で知識を移転するのではなく、**資産で行動を規定する**。文書標準が浸透しなかった組織で唯一機能するアプローチ。

**(2) 3階層の人材ラダー（100人の配分イメージ）**
| レベル | 対象 | 到達目標 | 施策 |
|---|---|---|---|
| L1 リテラシー | 全員（100名） | 承認ツールで日常業務を効率化。エージェントに仕事を「依頼」できる | eラーニング＋ハンズオン半日。Gemini/Copilotから開始 |
| L2 エージェント実践 | 開発者の大半（60〜70名） | ハーネス整備済みリポジトリでエージェント駆動開発ができる。スキルを書ける | 灯台チームでのOJT、CoP、社内スキルコンテスト |
| L3 ハーネス/ループ設計 | チャンピオン＋CoE（12〜15名） | ハーネスを設計し、自律ループを構築・運用できる | CoE伴走、フロンティアウォッチへの参加、外部コミュニティ |

**(3) 灯台チーム方式の実地移転**
- パイロット2〜3チームにCoEメンバーが数週間「埋め込み」で伴走し、ハーネス構築を実地で移転。
- 伴走終了時に、そのチームのチャンピオンが次のチームの伴走に参加する「**教えることで定着させる**」連鎖（10チームを Phase 2 で一巡）。

**(4) フロンティアウォッチループ — 「追いつく」を自動化する**
- 週次: エージェントが最新動向（リリースノート、論文、実践記事）を自動収集・要約 → CoEが15分レビューで「試す/見送る」を判定。
- 月次: 「試す」判定の技術をサンドボックスで検証 → 有効ならハーネステンプレート/ガイドラインを更新 → マーケットプレイス経由で全チームに自動配布。
- **これ自体がループエンジニアリングの部門内初号機**であり、ドッグフーディングになる。
- 効果: 個人が世の中を追う負担を、組織の仕組みに転換。テンプレート更新に追従するだけで全員が最新の型を維持。

**(5) 振り回されないための技術選定原則**
- 可搬性のある抽象に投資する: スキル（Markdown資産）、MCP（業界標準プロトコル）、AGENTS.md（ツール非依存）はツールを乗り換えても持ち運べる。特定ツールの独自機能への深い依存は避ける。
- 四半期ごとにツールポートフォリオを再評価（乗り換え判断はCoE）。

## 5. ロードマップ（規模反映版）

### Phase 0: アセスメント＋準備（2ヶ月）
- 10チームの活用実態・スキル調査、50システムの棚卸しと文書化優先度付け（変更頻度×障害頻度×有識者の残存性でスコアリング → 上位10システムを Phase 1-2 対象に）
- DX Core 4ベースライン測定開始、L1ガバナンス初版、承認済みサービスの調達手続き

### Phase 1: 基盤最小構成＋灯台チーム（3〜6ヶ月）
- マーケットプレイス＋標準ハーネステンプレートv1（企画者の既存資産をベースに）＋コストダッシュボード
- 灯台チーム2〜3チームで並行パイロット:
  - トラックA: レガシー文書化（優先上位3〜5システム）— 効果を数字で示す
  - トラックB: ハーネス整備済みリポジトリでのエージェント駆動開発
- L1教育を全員に実施、フロンティアウォッチループ稼働開始

### Phase 2: 横展開＋運用AI（6〜12ヶ月）
- 灯台チームの型を残り7〜8チームへ展開（伴走連鎖方式）、文書化を10システム完了→次の15システムへ
- AI SRE導入（障害一次調査・報告書ドラフト）、ナレッジ自動蓄積パイプライン稼働
- L2教育（開発者の大半をエージェント実践レベルへ）

### Phase 3: 自律化（12ヶ月〜）
- 夜間/イベント駆動の自律ループを標準装備化（テスト補強、依存更新、ドキュメント鮮度維持）
- AI SREをリカバリ支援まで拡大、ナレッジの蓄積→活用の完全ループ
- 効果報告と投資再配分、残り25システムの文書化

## 6. 推進体制（100人規模版）

```
経営スポンサー（役員1名）
   │
AI CoE（専任3〜5名）
 ├─ リード（1名）: 戦略・ガバナンス・フロンティアウォッチ判定
 ├─ プラットフォーム（1〜2名）: 基盤②〜⑥の構築運用
 └─ イネーブルメント（1〜2名）: 教育・伴走・スキル収集
   │
チームチャンピオン（各チーム1名×10、兼務20%目安）
   └─ Community of Practice（隔週、CoE が運営）
```

- 100人規模なら専任3名でも開始可能（プラットフォームは既存ツールの組み合わせが主で、ゼロから作るものは少ない）。
- 初期のハーネス知見は企画者に集中しているため、**属人化リスクをテンプレート化・伴走連鎖で早期に解消する**ことを体制設計に明記。
- セキュリティ・情シス・（Databricks運用チーム）はバーチャルメンバーとして月次レビューに参加。

## 7. 検討項目（関係者検討用の選択肢整理）

### 検討項目A: ナレッジ基盤の置き場（Databricksの守備範囲）

| 案 | 概要 | 長所 | 短所/リスク |
|---|---|---|---|
| A-1 Databricks集約 | 開発ナレッジも業務データもGenie Ontology/Lakebaseに集約 | ガバナンス一元化（Unity Catalog）、データ系ナレッジとの横断、既存投資の活用、エージェントメモリ・評価機能が揃う | 開発ツールチェーン（GitHub）から遠い。コーディングエージェントからの参照に一段レイヤが挟まる。DBU コスト増 |
| A-2 分離 | 開発ナレッジはGitHub近接（リポジトリ内ドキュメント＋RAG）、業務・データ系はDatabricks | ハーネスから直接参照でき開発者体験が良い。ドキュメントがコードと同じレビューフローに乗る | 二重管理。横断検索が弱い。ガバナンスが分散 |
| A-3 フェデレーション（推奨候補） | ソースオブトゥルースは「使う場所の近く」（コード系→リポジトリ、データ系→Databricks）。**MCPで相互接続**し、どちらのエージェントからも横断検索可能に | 2026年の業界標準構成。各系の開発者体験を損なわない。段階導入できる | MCPゲートウェイの構築・権限透過の設計が必要 |

**判断基準**: ①主な利用者は誰か（コーディングエージェント vs 業務エージェント）②更新頻度と更新者 ③権限モデルの透過性 ④ランニングコスト。
**推奨の方向性**: A-3 を基本とし、Phase 1 ではコード系（リポジトリ内）から開始、Phase 2 で Databricks 側と MCP 接続。Databricks運用チームとの役割分担協議が前提。

### 検討項目B: コスト予算モデル

| 案 | 概要 | 長所 | 短所/リスク |
|---|---|---|---|
| B-1 CoE一括 | 全AI費用をCoE予算で負担 | 活用促進期に「使い控え」が起きない。統制が容易 | 部門のコスト意識が育たない。CoE予算が膨らむ |
| B-2 部門配賦 | 利用実績で各チームに配賦 | コスト意識。受益者負担で公平 | 従量課金への萎縮 → 「最先端重視」方針と矛盾。導入初期には不適 |
| B-3 段階移行（推奨候補） | 初年度はCoE一括＋チーム別上限アラート。効果測定が成熟した2年目から配賦へ移行 | 促進と統制の両立。移行時には「効果あたりコスト」で語れる | 初年度予算の確保が必要 |

**推奨の方向性**: B-3。初年度は「投資フェーズ」と明確に位置づけ、ダッシュボードで異常利用のみ統制。

### 検討項目C: その他（企画書では「今後の検討事項」章に記載）
1. パイロット（灯台）チームの選定基準と候補
2. 文書化する50システムの優先度スコアリングの重み付け
3. Claude調達形態（Team/Enterprise/API直）とシート数の初期値（目安: L3層15名＋灯台チーム分で20〜30）
4. AI SREを内製（Claude Code＋MCP）か製品導入かの比較評価時期
5. 評価制度・目標設定へのAI活用度の組み込み方（チャンピオンのインセンティブ）

## 8. 投資対効果（フレーム）

- 投資: ライセンス/従量費用（100名 Copilot＋20〜30名 Claude）、CoE人件費（専任3〜5名）、教育、基盤構築（小規模）
- 効果（測定はDX Core 4）:
  - 生産性: 変更リードタイム短縮、節約時間（業界平均 3.6h/週/人 → 100人で年間約1.8万時間相当がベンチマーク）
  - 品質: 変更失敗率を悪化させない（AI起因不具合率を併測）
  - 運用: MTTR 30%削減、障害報告書作成時間 80%削減
  - レガシー: 文書化工数 90%以上削減（先行事例97%）、設計書カバレッジ 50システム中10→25→50
  - 組織能力: L2到達者数、スキル再利用数、テンプレート追従率

## 9. リスクと対策

| リスク | 対策 |
|---|---|
| 知見の属人化（企画者依存） | ハーネスのテンプレート化、伴走連鎖、フロンティアウォッチの複数名運営 |
| 「型」の押し付けによる現場反発 | L3は部門所有を堅持。共通化は「全員が速くなるものだけ」原則。CoPで現場発の改善を吸い上げ |
| AI出力の品質事故 | Human-in-the-Loop基準、CI不変条件、AI起因不具合率の測定 |
| コスト超過 | ダッシュボード＋チーム別上限アラート（B-3） |
| ツール陳腐化 | 可搬性のある抽象（スキル/MCP/AGENTS.md）への投資原則、四半期ポートフォリオ再評価 |
| 底上げの停滞（L1止まり層の固定化） | 教育をツール操作でなく「仕事の依頼の仕方」に焦点化。チャンピオンによるチーム内日常支援 |
