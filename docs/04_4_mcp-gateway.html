MCPゲートウェイ — エージェントの社内アクセスを一元統制

エージェントが社内システムに触る経路をここに集約し、認証・権限（利用者と同一）・監査・レート制御を担保する。「自由に使わせるための、たった1つの関所」。

1. 何を解決するか

エージェントに社内システム（チケット・監視・Wiki・DB）を触らせた瞬間、セキュリティの論点が爆発する。ツールごと・チームごとに個別接続を許すと、 権限の把握不能・監査不能・野良サーバーの混入が必ず起きる。ゲートウェイはこれを構造的に解決する2026年の標準構成[1]。

2. リクエストの流れ（統制の実体）

1. 呼び出しエージェント（Claude Code／coding agent／AI SRE／自律ループ）がツールを要求
→
2. 認証SSO連携。「誰の代理か」を特定（AgentCore Identity）
→
3. 認可利用者と同一権限にマッピング。範囲外は拒否
→
4. 実行承認済みレジストリのツールのみ呼び出し（レート制御つき）
→
5. 監査誰が・何を・いつ読み書きしたかを記録 → コスト帰属を⑤へ

2-1. 実装 — 自社開発しない（AWSマネージド第一）

段階実装内容
Phase 1
レジストリのみ		承認済みMCPサーバー一覧（JSON）＋ managed settingsで配布接続可能なサーバーをリストで統制。ゲートウェイ実体はまだ作らない — 軽く始める
Phase 2
データ系ツール		Databricks managed MCP ＋ Unity AI Gateway[4]テーブル・UC関数・SQL・Genie・Vector Searchは設定だけでMCPツール化でき、Unity Catalog権限がそのまま透過する。外部MCPサーバーへのアクセス統制とトラフィック可視化もUnity AI Gatewayが提供
Phase 2
API・Lambda系ツール		Amazon Bedrock AgentCore Gateway[3]AWS上の社内REST API・LambdaをMCPツールに自動変換（semantic routing）。Identityで権限透過、Observabilityで監査。接続先追加＝Lambda1本になる
代替候補Kong・Composio等のMCPゲートウェイ製品／OSS[1]上記2系統で不足が出た場合の比較対象（マルチクラウド要件等）

使い分けの基準は接続先の所在と権限体系 — Unity Catalog配下のデータ資産か、AWS上のAPI・運用ツールか。実行系統が2つになっても、レジストリ（承認済み一覧）と監査・可視化（⑤）の管理は1つに保つ。実装方式の確定は検討項目E-4（→ ⑧の3類型表）で行う。

3. 運用

新規サーバー追加時
申請（用途・データ分類・権限範囲）→ AI推進チーム＋セキュリティ担当が審査（1週間SLA）→ レジストリ登録 → 全エージェントから利用可
週次（自動）
異常パターン検知: 権限拒否の多発・深夜の大量読み出し・未知サーバーへの接続試行をアラート
月次
監査ログレビュー（セキュリティ担当）。利用ゼロのサーバー棚卸し
四半期
権限マッピングの見直し（組織変更・システム追加への追従）
L1ルールとの接続 「エージェントの社内接続は④経由のみ。レジストリ外の野良MCPサーバー接続は禁止」をL1ルールに明記。managed settings（②）のdenyで技術的にも強制する。

5. 事例と落とし穴

事例 Uber: ゲートウェイ＋レジストリで社内1万サービスの統制利用（月間アクティブエージェント1,500）[2]。 Block: 既定MCPサーバー整備で全社トークン-98.7%[2]。 ゲートウェイは「エンタープライズAIのコントロールプレーン」と位置づけ（Forbes）[1]。
落とし穴（反面教師） 野良MCPサーバー（サプライチェーン攻撃の入口。レジストリ制＋deny設定で遮断）／ トークン素通し（token passthrough）（ゲートウェイが権限を確認せず認証情報を転送すると権限昇格の穴になる — ゲートウェイ側での再認可を必須に）／ 最初から重厚に作る（Phase 1はリストだけ。統制を先に完成させると活用が死ぬ）／ 読み書き同時開放（新規接続は読み取り専用から始め、書き込みは実績を見て開放）。
