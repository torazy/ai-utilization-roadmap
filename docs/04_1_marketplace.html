L2 共通基盤 詳細 ①

社内スキル／プラグイン・マーケットプレイス

各チーム・各個人の工夫を「1回作れば100人が使える資産」に変える配布チャネル。実体は社内Gitリポジトリ1つ — 最も安く、最初に作るもの。

1. 何を解決するか

個人止まり
良いプロンプト・スキルが個人のメモやチャット履歴に埋もれている
車輪の再発明
10チームが同じ「レビュー観点」「設計書生成」を別々に作っている
数日
マーケットプレイス経由なら、良い工夫が全チームに届くまでの時間
設計上の位置づけ 最先端の型（②ハーネス、⑦ウォッチの成果）を全員に配る配布インフラでもある。①がないと、②⑦は「作ったが届かない」で止まる。

2. 技術構成

2-1. リポジトリ構造（これだけで成立する）

# 社内Git: github.com/<org>/ai-marketplace （リポジトリ1つ）
ai-marketplace/
├── .claude-plugin/
│   └── marketplace.json        # カタログ定義（下記）
├── plugins/
│   ├── common-dev/             # 共通開発（AI推進チーム管理）
│   │   ├── .claude-plugin/plugin.json
│   │   ├── skills/
│   │   │   ├── review-checklist/SKILL.md    # レビュー観点
│   │   │   ├── gen-design-doc/SKILL.md      # 設計書生成
│   │   │   └── impact-analysis/SKILL.md     # 影響調査
│   │   ├── agents/refactor-planner.md       # サブエージェント定義
│   │   ├── commands/                        # /コマンド
│   │   └── hooks/hooks.json                 # コミット前チェック等
│   ├── legacy-doc/             # レガシー文書化（Phase 1の主役）
│   ├── ops-incident/           # 障害対応（⑥と連動）
│   └── team-payment/           # チーム固有（L3・各チーム所有）
└── CONTRIBUTING.md             # 公開手順・昇格基準
// .claude-plugin/marketplace.json（最小構成）
{
  "name": "company-ai-marketplace",
  "owner": { "name": "AI推進チーム" },
  "plugins": [
    { "name": "common-dev",  "source": "./plugins/common-dev",
      "description": "共通開発スキル: レビュー・設計書・影響調査" },
    { "name": "legacy-doc",  "source": "./plugins/legacy-doc",
      "description": "レガシー文書化: コード→設計書リバース生成" }
  ]
}

利用者側は1コマンドで導入・同期:

claude plugin marketplace add github.com/<org>/ai-marketplace
claude plugin install common-dev   # 以後 git pull で自動的に最新化

2-2. ツール非依存に保つ（乗り換え耐性）

資産置き方各ツールからの利用
スキル本体Markdown（SKILL.md）— 手順・知識・例を記述Claude Code: そのまま ／ Copilot: instructionsファイルへ変換 ／ Gemini CLI: 拡張として読込
ツール別アダプタ薄い変換層のみ（自動生成スクリプト）マルチハーネス対応のOSS実装が参考になる[2]
MCPサーバー定義plugin内の mcp.json（接続先は④のレジストリ準拠）MCP対応ツールすべて共通
原則 知識・手順はMarkdownに書く（ツール中立）。特定ツールの独自形式に直接書くのは変換層だけ。これでツール乗り換え時も資産が生き残る。

3. 運用 — スキルのライフサイクル

1. 作る個人が業務の中でスキル化。テンプレは common-dev/skill-template
→
2. チーム公開team-* プラグインに置くだけ。審査なし・即日
→
3. 昇格申請他チームでも使えそうなものをチャンピオンが推薦
→
4. レビューAI推進チームが品質ゲート（下記チェックリスト）
→
5. 共通配布common-* へ移動 → 全チームに数日で自動同期

※ ステップをクリックで固定表示（ホバーで一時停止）

昇格レビューのチェックリスト（品質ゲートはここだけ）
  • 汎用性: チーム固有の前提（システム名・パス）が除去またはパラメータ化されているか
  • 安全性: 破壊的操作を含む場合、確認ステップ・denylistがあるか
  • 検証可能性: 期待する出力の例（正解サンプル）が添付されているか — ⑦の評価シナリオに転用
  • 説明: description 1行で「いつ使うか」が判るか（発見性）
  • 重複: 既存共通スキルと統合できないか
週次・月次・四半期の運用カレンダー
随時（自動）
スキル利用回数を⑤に送信（OTelイベント）。壊れたスキルはIssue自動起票
月次（30分・AI推進チーム）
昇格申請のレビュー、非推奨化（3ヶ月利用ゼロは deprecated タグ）
四半期（CoP内）
利用数ランキング公表・作者表彰。スキルコンテスト（お題つき）

初期コンテンツ（Phase 1着手時に用意する12本）

プラグイン初期スキル
common-devレビュー観点 ／ テスト作成 ／ 影響調査 ／ PR説明文生成 ／ コミット規約
legacy-docコード→設計書リバース生成 ／ 依存関係マップ ／ ビジネスルール抽出 ／ AGENTS.mdドラフト生成

※ 企画者の既存ハーネス資産を核に、灯台チームの実務で磨いてから共通化する。

4. KPIと計測方法

指標取得方法目安
共通スキル数／チームスキル数リポジトリの集計（CIで自動）6ヶ月で30本／50本
スキル利用回数・利用チーム数Claude CodeのOTelイベント（ツール実行ログ）→⑤へ[3]再利用率（2チーム以上で利用）50%
時間短縮スキル化前後の作業時間をチャンピオンがサンプル計測（対象作業3つ/四半期）対象作業で1/5（先行事例: 15分→2分[4]）

5. 事例と落とし穴

事例 Thoughtworks Technology Radarが社内Git配布モデルを評価[1]。国内では50本超のスキル運用（見積書15分→2分）事例[4]。 メルカリは専任部隊が標準を全社展開し利用率95%を達成[5] — 「作る人」と「届ける仕組み」の両輪が成功要因。
落とし穴（反面教師） 審査を厳しくしすぎて投稿が止まる（チーム内公開は無審査を貫く）／ 類似スキルの乱立（月次の統合レビューで対処）／ 作りっぱなしの陳腐化（利用ゼロ3ヶ月で自動deprecated。壊れたら自動Issue）／ 野良MCPサーバーの混入（接続先は④の承認済みレジストリに限定 — L1ルール）。
