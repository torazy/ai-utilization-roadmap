2. 主張別の検証結果

✅ 公開情報で裏付けが取れた主張

記事の主張裏付け（一次情報）
メタハーネス論文が公開され、ハーネス自体の自動最適化が研究段階に入ったMeta-Harness (arXiv 2603.28052, Stanford) — ハーネスコードを外側ループで探索・最適化。TerminalBench-2で手設計ハーネスを上回る。実在確認 ✅
Claude CodeのAgent Teams（リーダー＋チームメイト、SendMessage/共有タスクリストで協調）公式Docs: Orchestrate teams of Claude Code sessions — Opus 4.6と同時に2026年2月リリースの実験的機能。2〜16エージェント、メールボックス＋共有タスクリスト ✅（「Opus 4.6」という記事中のモデル名も実在確認）
会話が長いほど判断が鈍る（コンテキスト劣化）。Chromaが18モデルで実測Chroma: Context Rot — 18モデル全てで入力長の増加とともに性能劣化。上限のはるか手前で非線形に悪化 ✅
入力のヒントに引きずられ、思考過程はそれを言わない（バイアスは非自覚）Anthropic: Reasoning Models Don't Always Say What They Think — 論文実在。ヒント利用の言語化率が低い方向性は一致 ✅（記事中の「99%超/2%未満」という個別数値は本文未確認 ⚠️）
RALPHループ（無限リトライ）は粘るが採点者不在が欠陥Geoffrey Huntley: Ralph — 原型実在。「採点設計＋機械的続行判定を足す」という記事の拡張は妥当 ✅
スキルの context: fork（まっさらな別コンテキストで実行）と disable-model-invocation公式Docs: Skills — 両フィールドとも実在。fork＝独立サブエージェント実行 ✅
指示を増やすほど個々の遵守率が下がる（CLAUDE.md肥大の逆説）IFScale (arXiv 2507.11538) — 指示密度の上昇で遵守率が減衰（最高モデルでも500指示で68%）。方向は一致 ✅（記事中の「10個→90%/30個→70%」という具体数値はこの論文にはない ⚠️）
MCPよりCLIが帯域面で有利（ツール定義がコンテキストを常時占有）Mario Zechner: MCP vs CLI — ベンチマーク実在。MCPツール定義でコンテキスト7〜9%消費の実測あり。ただし彼自身の結論は「プロトコルよりツール設計の質が支配的」＋CLIは毎回セキュリティチェックのトークンコストがある。記事の「CLIファースト」は一面の簡略化 ⚠️
自己申告は完了の証拠にならない（長時間エージェントで顕著）Anthropicの長時間稼働エージェントに関するエンジニアリング発信・SWE-benchの設計思想（自己申告を排しテストで判定）と整合 ✅
報酬ハッキング（テスト改変・リンター無効化で「点だけ取る」）OpenAIのRL研究（specification gaming）・DORAのガードレール議論と整合。評価基準ファイルをdenyで保護する対策は公式のPermissions機構で実装可能 ✅

💡 著者の実践知・仮説（裏付けは自身の運用のみ — 有用だが検証して使う）

マクロ／ミクロ／Project OSの3要素論著者自身が「検証中の仮説」と明言。ただし内容は本企画の整理と同型（マクロ≈狭義ループの制御層、ミクロ≈②ハーネス、Project OS≈状態基盤/チケット）。相互裏付けとして心強いが、用語は当社では公開標準（ハーネス/ループ/AGENTS.md）に寄せる
スキルの4分類（辞書型/手順型/生成手順型/アイデンティティ型）公式は2分類相当。4分類は著者の拡張。設計指針としては実用的 — スキルテンプレの「型」の参考に
同一レビュアーの再利用で採点が甘くなる（3.7→3.9→4.1）→ kill&spawn（コンテキストフレッシュ）LLM-as-a-judgeのバイアス研究（自己強化・スコアドリフト）と整合する観察。fork起動の運用で対処可能
採点者の4契約（fork起動・基準書換禁止・絶対評価・実物確認）、採点JSONのスキーマ固定報酬ハッキング対策として理にかなう。当社ループテンプレに採用価値が高い
依頼文=採点表（あいまい形容詞を数えられる事実に翻訳）評価設計の実務知。SWE-bench等の「テストで完了を定義する」思想の一般化として妥当
本質ドキュメント（不変原則の明文化＋PR駆動更新＋HITL）実質は「レビュー基準のコード化」。当社では②の評価エージェント基準書として採用可能

❓ 未確認・注意が必要な記述

製品名・モデル名の一部「OpenCrew」「Symphony（監督レール）」「GPT-5.4/5.5」「GLM-5」は今回の検索では確認できず。企画資料には転記しない
具体的な数値の一部「指示10個→遵守90%」「ヒント使用99%/言及2%」等は出典の数値と一致確認できず（方向は正しい）。数字は必ず一次情報の値に差し替えて使う
トークン消費5〜30倍ループ化のコスト増は確実だが、倍率は著者の体感値。当社では⑤で実測して自前の係数を持つ

3. 冷静な判断 — 採用にあたっての注意5点

① 単一著者・Claude Code特化実践知はほぼClaude Codeエコシステム前提。当社はCopilot/Gemini/Databricksを併用するため、可搬な原理（生成と評価の分離、状態外部化、機械的続行判定）だけを抽出し、ツール固有の手筋はテンプレ実装の参考に留める
② 個人規模→組織規模の翻訳著者の運用は1人〜数人。100人組織では「採点軸を誰がレビューするか」「ループの承認・監査」など統治の層（本企画のL1/④/⑤）を足す必要がある — ここは記事に無い、当社企画の付加価値
③ 著作権・利用条件記事は購入者限定・転載/共有禁止と明記。部門配布資料への原文・図の転載、独自用語体系の丸写しは行わない。本シリーズの詳細ページは、同じ主張を公開一次情報（論文・公式Docs）で裏取りし、自分たちの言葉で記述する方針を維持する
④ 陳腐化の速さAgent Teams（実験的機能）、Stop hookの仕様等は数ヶ月で変わり得る。⑦フロンティアウォッチの監視対象に「Claude Code changelog」を既に含めており、これで追従する
⑤ 著者自身の留保「正解ではなく検証しやすい形の仮説」「うまく回らないときは責務か状態を疑う」— この態度ごと採用する。当社でも各テンプレは灯台チームの実測で検証してから展開（既定のプロセスと一致）
