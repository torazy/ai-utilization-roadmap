エグゼクティブサマリ

各部署が個別に進めてきた生成AI活用を、部門共通の「イネーブルメント基盤」と「機械可読な開発標準（ハーネス）」に集約し、 開発から運用・ナレッジ・データ利活用までを一貫してAIエージェント駆動へ変革する。

世界的にAIパイロットの88%が基盤（ガバナンス・環境・評価）の欠如で本番化に失敗しており[3]、 「AIは増幅器 — プラットフォーム投資こそが価値実現の条件」がDORA 2025の結論[16]。 本企画はDX部門内の専任チーム「AI推進チーム（CoE）」3〜5名を核に、18ヶ月で 生産性+19%以上・MTTR-30%・レガシー文書化工数-90%の実現と、 技術進化に自動追従する組織能力の獲得を狙う。

施策の全体像 — 3層モデル

共通化するのは「全員が速くなるもの」だけ。業務固有は部門所有（L3）を堅持する

ツール使い分け — 製品名ではなく「3つの軸」で決める（L1方針）

GitHub Copilot にもエージェント機能がある（IDE内で自律的に編集する agent mode、Issueを割り当てるとGitHub Actions上で作業しPRを返す coding agent＝2026年3月GA[20]）。 したがって「Copilot＝補完、Claude＝エージェント」という製品での分担は成立しない。タスクの性質を次の3軸で見て選ぶ。

軸1 自律度

同期補完 → IDE内エージェント → 非同期委任（Issue→PR） → 常駐自律ループ。右に行くほどハーネス（②）が前提になる。

軸2 実行場所

開発者の手元（IDE・端末）か、クラウド（GitHub Actions／AWS上）か。非同期・常駐型はクラウド実行になる。

軸3 文脈の広さ

GitHub内で完結するか、MCPで社内システム・ナレッジを横断するか、データ基盤（Databricks）の中か。文脈がすでにある場所のツールを使う。

使い分け一覧（軸で整理した改訂版）

タスクの性質使うもの備考
手を動かしながらの補完・小修正（同期・IDE）Copilot 補完＋agent mode全員配布。最も低単価・低レイテンシ
GitHub内で完結する非同期の定型タスク（バグ修正・依存更新・テスト追加のIssue→PR）Copilot coding agentActions上で実行。複雑タスクはpremium request 10〜30件/回を消費するため⑤で監視[20]
深い文脈・社内横断の作業（レガシー解析、大規模リファクタ、MCP経由で監視・チケット・ナレッジを参照）Claude Codeハーネス（②）前提。L3層＋灯台チーム20〜30名から
常駐・スケジュール駆動の自律ループ（夜間のテスト補強・文書鮮度維持・依存更新）Claude Code ＋ Actions／AgentCore Runtime狭義のループエンジニアリング領域（Phase 3）。実行場所は検討項目D-3
非開発業務（資料・議事録・メール）Gemini (Workspace)全社員ライセンス済み。非エンジニアの入口
データ分析・業務エージェント・ナレッジDatabricks (Genie / Agent Bricks)既存契約。Unity Catalogでガバナンス統合
障害調査・報告（イベント駆動）AI SRE（AWS DevOps Agent第一候補）提供システムがAWS上のため。内製と比較（C-4）
判断原則（迷ったときの優先順） ① 文脈がすでにある場所で — GitHubで完結する仕事はCopilot系、社内横断はClaude系、データ基盤の中はDatabricks系。 ② 同等なら低単価な方 — 同じ自律度帯で両方できるなら安い方を使う。 ③ 自律度を上げる前にハーネス — ②なしで非同期委任・自律ループに進まない（88%失敗の轍[3]）。 境界の細部（coding agentの適用範囲等）は検討項目D-1で確定する。
2026年上期の変化: 「モデル」と「ハーネス」の選択は分離した Copilot Business/Pro内でClaudeやCodexをエージェントのモデルとして選択可能になり（2026年2月〜、JetBrains対応は6〜7月に拡充[26]）、 「どのモデルを使うか」と「どのハーネス（実行環境・統制・文脈）で使うか」は別の意思決定になった。 製品名でなく自律度×実行場所×文脈の3軸で選ぶ本マトリクスの枠組みは、この変化後も有効に機能する。
セキュリティ前提 いずれも学習に利用されない（no-training）構成での契約・設定を承認条件とする。データ分類×投入可否マトリクスをL1で整備。 ClaudeはAmazon Bedrock経由ならプロンプト・コードがAWSアカウント内に留まる構成が可能（→ AWS構成・検討項目D-2）。

共通イネーブルメント基盤（L2）の詳細

設計思想: 「基盤を使え」と言わない。普段の作業が自然に基盤を通る構造にし、統制点は④と⑤の2箇所だけに絞る

⑧ Fast-Trackレーンと共通APIゲートウェイ（v0.5追加 — 整備を待たせない受け皿）

「業務でLLM APIを使いたい」等の現在進行形の要望を止めずにガバナンスへ乗せる仕組み。 原則は「禁止でも放任でもなく、舗装された道を最速で提供する」（Paved Road）。 申請3問→低リスクは即日〜翌日承認→共通ゲートウェイの仮想キー（予算・レート制限・用途タグつき）を払い出し→利用ログとコストは自動で⑤へ→90日レビューで本則化/停止。 整備期間中に増える様々な要望も、インテーク一本化（既存の道に乗せる／舗装計画に反映／例外審査の3分類）で受ける。 受け皿はAPIに限らず、MCPツールの提供（暫定登録レーン: 読み取り専用＋ログ必須で即日）とエージェント構築（Tier 1は即時、書き込み系は例外審査）も同じインテークに乗せる。 ゲートウェイ実装は原則Unity AI Gateway・例外条件でBedrock直（検討項目E）。 Phase 0から前倒しで稼働開始し、現在のAPI要望を第1号灯台案件にする。詳細は⑧詳細ページ。

導入前後の変化

BEFORE — 対話的利用（現状）
  • 人が毎回プロンプトで文脈を説明
  • 出力は人が目視で全チェック
  • 標準は文書。読まれず浸透しない
  • 個人PCの環境差で再現に失敗
  • 1人1エージェントの対話が限界
AFTER — ハーネス整備後
  • AGENTS.mdが常時文脈を供給。指示は「何を」だけ
  • 評価エージェント＋CIが一次チェック。人は判断に集中
  • 標準はエージェントが従うので「実行」される
  • devcontainerで誰でも・どのエージェントでも同一環境
  • worktree分離で複数タスク並行 → 自律ループへ
効果定量目安根拠
エージェントタスクの成功率・手戻り大幅改善（88%失敗の轍を回避）失敗要因は基盤欠如[3]
レビュー負荷機械的指摘をCIが先取りCI不変条件[8]
開発標準の浸透率導入リポジトリ数で初めて測定可能に—
事例 OpenAI Codexチームは「AGENTS.md＋再現可能環境＋CI不変条件」の3点セットで自社開発を運用[8]。 Anthropicは計画・生成・評価を分離した3エージェントハーネスで長時間の自律フルスタック開発を実証[9]。

MCPゲートウェイ — 統制点その1

Phase 1末〜
目的: エージェントが社内システムに触る経路を1箇所に集約し、認証・権限・監査・レート制御を一元管理。「エージェントは代行するユーザーと同一権限」の原則を技術的に担保する。

認証・認可

SSO連携。エージェントの権限を利用者と同一にマッピング

監査・帰属

誰のエージェントが何を読み書きしたかを記録。コストは⑤へ帰属

レジストリ

承認済みMCPサーバー一覧。野良サーバー接続はL1ルールで禁止

段階導入: Phase 1は「承認済みサーバーのリスト管理」のみで軽く開始 → Phase 2で集中統制へ。 実装は自社開発せず、接続先の所在で使い分ける — データ系ツールはDatabricks managed MCP＋Unity AI Gateway（設定でMCP化・Unity Catalog権限透過）、AWS上のAPI・Lambda系はAgentCore Gateway（Identity＋監査）。 レジストリと監査の管理は一元に保つ（→ AWS構成・検討項目E-4）[21]。

効果定量目安根拠
エージェント経由のデータ事故権限透過＋監査で構造的に防止ガードレール標準構成[14]
新規ツール接続サーバー1本追加で全エージェントから利用可MCP標準化の効果[15]
セキュリティレビュー個別ツールごと → 1点に集約—
事例 UberはMCPゲートウェイ＋レジストリで社内1万超のサービスをエージェントから統制利用（月間アクティブエージェント1,500、週6万実行）。 Block（Square）は既定MCPサーバー整備等により全社トークン消費−98.7%を達成[15] — 基盤整備がそのままコスト削減になる代表例。

コスト・効果ダッシュボード — 統制点その2

Phase 1〜
目的: 従量課金時代のAIコストをチーム別・用途別に可視化し、同じ画面で効果（DX Core 4）と並べる。「使いすぎの統制」ではなく「成果あたりコスト」での経営報告を可能にする。

コスト面（FinOps for AI[18]）

  • ツール別支出（Copilot／Claude／Databricks）を各ベンダーAdmin APIから集約
  • チーム別・用途別の帰属（④のログ＋APIキーのタグ付け）
  • チーム別上限アラート（青天井の防止）
  • 成果あたりコスト: ¥/PR、¥/障害対応

効果面（DX Core 4[16]）

  • 変更リードタイム／デプロイ頻度／変更失敗率
  • 節約時間（h/週/人）、AI起因不具合率
  • 活用度: 利用率、スキル利用回数、ハーネス導入数（/50システム）
  • 実装はDatabricks上の自作も現実的（データ基盤が既にあるため）
POINT 「測定なしのAI導入は改善が停滞する」がDORA 2025の結論[16]。ベースライン測定は企画承認前（Phase 0）から開始し、効果主張の説得力を確保する。
⑥

AI SRE — 運用工程のAI化

Phase 2〜
目的: 障害対応の「調査・整理・報告」をAIに移し、人間は判断と意思決定に集中する。対応記録は③に自動蓄積され、対応するほど賢くなる。

3段階の導入ステップ

Step 1: 一次調査アラート発火→監視・ログ・デプロイ履歴・過去事例を横断し、5分以内に「状況＋原因仮説＋類似事例」を投稿
→
Step 2: 報告自動化対応ログから報告書ドラフト・タイムライン・再発防止案を生成→人間レビューで確定→③へ蓄積
→
Step 3: リカバリ支援ランブック化された定型対処を人間承認付きで実行（Human-in-the-Loop）
効果定量目安根拠
MTTR（平均復旧時間）−30%（先進事例は30〜70%）AI SRE導入企業の実績[17]

実行基盤 — AWS前提の構成（新規基盤製品は原則導入しない）

当社の提供システムはAWS上にあるため、L2基盤の実行環境も既存の3点 — AWS・GitHub・Databricks（on AWS）で構成する。 エージェント実行・接続統制・監視はAWSのマネージドサービス（Bedrock／AgentCore）を第一候補とし、自社開発を最小化する[21]。

Claudeの調達はBedrock経由が有力（→ D-2）

Claude CodeはBedrock接続をサポート。プロンプト・コードがAWSアカウント外に出ない（学習不使用）、請求がAWSに一元化、IAMで権限管理 — 「学習しない環境なら投入可」というセキュリティ前提を最も強く満たす[21]。

④MCPゲートウェイは自社開発しない（接続先の所在で使い分け）

データ系ツールはDatabricks managed MCP＋Unity AI Gateway（設定でMCP化・Unity Catalog権限が透過）、AWS上のAPI・Lambda系はAgentCore Gateway（Identityで同一権限・Observabilityで監査）。実行系統は2つでも、レジストリと監査の管理は一元に保つ（検討項目E-4）[21]。

自律ループの実行場所は2択（→ D-3）

GitHub Actions（コードに近い・導入容易・CI資産流用）か、AgentCore Runtime（セッション分離microVM・最長8時間・複数エージェント並行）か。Phase 3までに実測して決定。

AI SREはAWSネイティブが第一候補（→ C-4）

提供システムがAWS上のため、CloudWatch等のテレメトリに直結するAWS DevOps Agentを第一候補とし、内製（Claude Code＋MCP）とPhase 1末に比較評価する。

最先端引き上げ戦略

「人を教育して追いつかせる」は構造的に不可能。原則は「型に乗せる」×「追従を仕組み化する」

前提の用語整理 — 「ループ」には3つの階層がある（広義と狭義）

この整理により本企画の位置づけが明確になる: Phase 1〜2はハーネス（内側ループを安定させる投資）、Phase 3で狭義のループへ進み、⑦③⑤の広義のループはPhase 1から並行稼働させる。 「ハーネスなしにループなし」— 内側が不安定なまま外側を自動化すると失敗が量産されるため、この順序は崩さない。 6つの構成要素・自律ティア・停止条件・最初に回す3本のループ設計はループエンジニアリング詳説を参照。

原則 1  型に乗せる

最先端の実践（計画/生成/評価の分離、CI不変条件、スキル分割）をハーネステンプレートに焼き込んで配布。 開発者はテンプレートで作業するだけで最先端の型を「実行」する。知識移転ではなく、資産で行動を規定する — 文書標準が浸透しなかった組織で唯一機能するアプローチ。

原則 2  追従を仕組み化する

⑦フロンティアウォッチループが最新動向の収集・評価・展開を自動化。 個人が世の中を追う負担を、組織の仕組みに転換する。全員はテンプレート更新に追従するだけで最新の型を維持できる。

E-2Fast-Trackの権限設計低リスク即日承認の判定を誰が担うか（AI推進チーム専決の範囲）。例外審査（分類C）の合議体。90日レビューの判定基準
E-3本番組込みのSLAとワークロード分離業務システムに組み込む場合の可用性・レイテンシ・フォールバック要件と、例外条件（E-1参照）の該当判定基準。本番サービス利用と社内利用は実行資源を分離する（Unity AI GW: エンドポイント／ワークスペース分離＋本番はプロビジョンドスループット、Bedrock: アカウント分離＝クォータ独立）— 社内利用の障害・過負荷を本番に波及させないことを設計要件とする
E-4MCP提供の実装方式データ系ツール→Databricks managed MCP（UC関数・SQL・Genie・Vector Searchを設定で提供、Unity Catalog権限が透過）／社内API・Lambda系→AgentCore Gateway（④と同一基盤）／特殊要件のみ自作。いずれも④レジストリ登録を必須とし、暫定登録レーン（読み取り専用＋ログ必須で即日）で整備を待たせない → ⑧詳細の3類型表
