## 0. 全体アーキテクチャ

```
                        開発者 100名 / 10チーム / 50システム
                                      │
        ┌─────────────────────────────┼─────────────────────────────┐
        │          日常の開発・運用はすべて L2 基盤を「通る」          │
        ▼                             ▼                             ▼
┌──────────────┐    ┌──────────────────────────┐    ┌──────────────────┐
│ ① マーケット   │    │ ② 標準ハーネス            │    │ ⑥ AI SRE          │
│  プレイス      │───▶│   テンプレート             │    │  障害調査/報告     │
│ (スキル配布)   │    │ (各リポジトリに展開)        │    │                  │
└──────┬───────┘    └────────────┬─────────────┘    └────────┬─────────┘
       │                         │ エージェントが参照/実行       │
       │            ┌────────────▼─────────────────────────────▼──────┐
       │            │ ④ MCPゲートウェイ (認証・権限・監査の一元管理)      │
       │            └──┬──────────┬──────────┬──────────┬─────────────┘
       │               ▼          ▼          ▼          ▼
       │        ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────────┐
       │        │ GitHub  │ │ チケット │ │ 監視/ログ │ │ ③ ナレッジ基盤 │
       │        │         │ │ /Wiki   │ │         │ │ (Databricks) │
       │        └─────────┘ └─────────┘ └─────────┘ └──────▲──────┘
       │                                                   │ 自動蓄積
       │      ┌────────────────────────────────────────────┴──────┐
       └─────▶│ ⑦ フロンティアウォッチループ (最新動向→テンプレート更新) │
              └───────────────────────────────────────────────────┘
                                      │ 利用ログ・コスト・成果指標
                                      ▼
              ┌───────────────────────────────────────────────────┐
              │ ⑤ コスト・効果ダッシュボード (FinOps + DX Core 4)      │
              └───────────────────────────────────────────────────┘
```

**設計思想**: 開発者に「基盤を使え」と言うのではなく、①のスキル配布と②のテンプレートによって**普段の作業が自然に基盤を通る**構造にする。統制点は④（アクセス）と⑤（コスト・効果）の2箇所に集約する。

**構築の依存関係と順序**:

```
Phase 1        Phase 1後半         Phase 2            Phase 3
①──▶②─────────▶④──────────────▶③──▶⑥            (⑦は①②と同時に開始し
マーケット  ハーネス   MCPゲートウェイ  ナレッジ  AI SRE      以後回り続ける)
プレイス   テンプレート
└── まずGit1リポジトリで開始 ──┘   └─ Databricks連携 ─┘
```

## ① 社内スキル/プラグイン・マーケットプレイス

### 目的
各チーム・各個人に散在するプロンプト・スキル・ハーネスの工夫を「1回作れば100人が使える資産」に変える。最先端の型を全員に配る配布チャネル。

### 構成

```
社内Git (例: github.com/<org>/ai-marketplace)
├── .claude-plugin/marketplace.json   ← カタログ定義。これだけで成立 [^tw]
├── plugins/
│   ├── common-dev/          # 共通開発プラグイン (CoE管理)
│   │   ├── skills/          #  レビュー観点、テスト作成、設計書生成…
│   │   ├── agents/          #  リファクタ用/調査用サブエージェント定義
│   │   ├── commands/        #  /impact-analysis, /gen-design-doc …
│   │   └── hooks/           #  コミット前チェック等
│   ├── ops-incident/        # 運用・障害対応プラグイン (⑥と連動)
│   ├── legacy-doc/          # レガシー文書化プラグイン
│   └── team-<name>/         # チーム固有 (L3。各チームが所有)
└── CONTRIBUTING.md          # 公開手順 (下記の昇格フロー)
```

利用者側は `claude plugin marketplace add <社内リポジトリ>` の1コマンドで全スキルが使える。Copilot / Gemini CLI 等と共用できるマルチハーネス構成のOSS実装も存在するため、**特定ツールにロックインしない置き方**（スキル本体はMarkdown、ツール別アダプタは薄く）を採る[^multi]。

### 運用フロー（スキルの昇格）

```
個人の工夫 ──▶ チームプラグイン(team-*) ──▶ CoEレビュー ──▶ 共通プラグイン(common-*)
 (即公開可)      (チャンピオンが管理)       (3ヶ月サイクル)     (全チームに自動配布)
```

- 品質ゲートは共通昇格時のみ。チーム内は自由 — 統制で投稿意欲を殺さない。
- 四半期ごとに利用数ランキングを CoP で共有し、作者を表彰（インセンティブ設計）。

### 効果
| 指標 | 目安 | 根拠 |
|---|---|---|
| 定型作業の時間短縮 | 対象作業で 1/5〜1/7 | スキル化した見積書作成が15分→2分になった国内事例[^hexa] |
| スキル再利用数 | 6ヶ月で共通30本・チーム50本 | 1社で50本超のスキル運用事例あり[^hexa] |
| 最先端プラクティスの伝播速度 | テンプレート更新から全チーム反映まで数日 | Git同期による自動配布 |

> **事例注釈**: Thoughtworks Technology Radar は Claude Code プラグインマーケットプレイス（社内Gitでの配布モデル）を、チームへの共有手段として採用評価している[^tw]。メルカリは CTO 直轄の専任部隊が社内標準（Agent Spec駆動開発）を定めて全社展開し、**社内AIツール利用率95%・プロダクトコードのAI生成比率70%・開発量64%増**を公表している[^mercari] — 「工夫を組織資産にする専任機能」の効果を示す国内代表例。

## ② 標準ハーネステンプレート

### 目的
「浸透しなかった文書ベースの開発標準」を、**エージェントが従うことで自動的に実行されるリポジトリ内資産**として再定義する。50システムすべてを「エージェントが安全に作業できる状態」にするための共通の型。

### 構成（1リポジトリに配置するもの）

```
<各システムのリポジトリ>
├── AGENTS.md / CLAUDE.md      # ① 作業指示書: ビルド/テストコマンド、
│                              #    規約、触ってよい/いけない領域 [^codex]
├── .claude/  (or .github/)
│   ├── settings.json          # ② 権限・許可コマンドの統制 (managed settings) [^starter]
│   ├── skills/                # ③ このシステム固有のスキル
│   └── agents/                # ④ 計画/生成/評価を分離したサブエージェント [^anthro]
├── .devcontainer/             # ⑤ ワンコマンドで再現する開発環境 [^codex]
├── docs/design/               # ⑥ 設計ドキュメント (レガシーはAIリバース生成で作る)
└── CI パイプライン
    ├── 既存: ビルド・テスト
    └── 追加: 不変条件チェック   # ⑦ アーキテクチャ境界・命名・フォーマットを
                               #    機械的に強制。エージェントの暴走を止める柵 [^codex]
```

### ハーネスの働き（Before / After）

| | Before（現状: 対話的利用） | After（ハーネス整備後） |
|---|---|---|
| 指示 | 人が毎回プロンプトで文脈を説明 | AGENTS.md が常に文脈を供給。指示は「何をするか」だけ |
| 品質 | 出力を人が目視で全チェック | 評価エージェント＋CI不変条件が一次チェック。人は判断に集中 |
| 標準 | 文書。読まれず浸透しない | エージェントが従うので**実行される**。人間向けは副産物 |
| 環境 | 個人PCの環境差で再現失敗 | devcontainerで誰でも(どのエージェントでも)同一環境 |
| 並行性 | 1人1エージェント対話 | worktree分離で複数タスク並行 → Phase 3 の自律ループへ |

### 展開方法
- テンプレートリポジトリ＋導入スクリプト（半日で1システムに導入できる粒度にする）。
- 灯台チームで v1 を検証 → 伴走連鎖で10チームへ。**導入済みリポジトリ数がそのまま企画の進捗KPI**になる。

### 効果
| 指標 | 目安 | 根拠 |
|---|---|---|
| エージェントタスク成功率 | 大幅向上（手戻り削減） | ハーネスなしではエージェントの本番活用の88%が頓挫[^north]。計画/生成/評価分離で長時間自律開発が成立[^anthro] |
| レビュー負荷 | AI起因の指摘をCIが先取りし人的レビュー時間を削減 | CI不変条件による機械的強制[^codex] |
| 開発標準の浸透率 | テンプレート導入率で直接測定可能（従来は測定不能） | — |

> **事例注釈**: OpenAI Codex チームは AGENTS.md・再現可能環境・CI不変条件の3点セットで自社開発を運用[^codex]。Anthropic は計画・生成・評価を分離した3エージェントハーネスで長時間の自律フルスタック開発を実証[^anthro]。国内では Claude Code の managed settings（IT部門による統制）＋ Starter Kit（推奨設定の配布）という企業配布パターンが確立している[^starter]。

## ③ ナレッジ基盤（蓄積もAI・活用もAI）

### 目的
障害対応・設計判断・レビュー知見が個人の記憶やチャットログに消えている状態をやめ、**発生した瞬間にAIが構造化して蓄積し、次のAI実行のコンテキストとして自動供給される**ループを作る。

### 構成（検討項目A-3: フェデレーション構成を前提とした姿）

```
【蓄積側 — 人は何もしない】
 障害対応チャネル ─┐
 PR/レビュー ──────┼─▶ 収集エージェント ─▶ 構造化 ─▶ ┌─────────────────┐
 設計判断(ADR) ────┤   (イベント駆動)     (要約・タグ・  │ ナレッジストア      │
 定例議事録 ───────┘                     関係抽出)     │ ・コード系: リポジトリ│
                                                     │   内docs (Git管理) │
                                                     │ ・横断系: Databricks│
                                                     │   (Genie Ontology/ │
【活用側 — エージェントが勝手に引く】                     │    Vector Search)  │
 開発エージェント ◀──┐                                 └────────┬──────────┘
 AI SRE(⑥) ◀───────┼── ④MCPゲートウェイ経由で検索 ◀────────────┘
 Genie(業務分析) ◀──┘    (利用者と同一権限で)
```

- **ハイブリッド検索**（ベクトル＋キーワード＋リランカー）を標準にする。純粋なベクトル検索は専門領域で15〜20%外す、が業界の実測[^rag]。
- 鮮度維持も自律ループ化: 古い設計書とコードの差分をエージェントが夜間検出し、更新PRを起票（Phase 3）。

### 効果
| 指標 | 目安 | 根拠 |
|---|---|---|
| 類似障害の調査時間 | 過去事例の即時提示で大幅短縮（⑥と相乗） | AI SRE先行事例でMTTR 30〜70%減の一部を構成[^rootly] |
| 有識者への依存 | 退職・異動リスクの低減（50システムの暗黙知を資産化） | 富士通のリバース文書化: 工数97%減[^fujitsu] |
| ナレッジ鮮度 | 「書いた瞬間から陳腐化する文書」→ 自動追従 | 自己更新ナレッジベースの実用化[^rag] |

> **事例注釈**: Databricks の Genie Ontology は「組織の全ナレッジの自己改善するコンテキスト層」を掲げ、Lakebase によるエージェントメモリ、MCP ツールアクセスを提供[^dbx] — 当社の既存契約で使える範囲が広い。エンタープライズRAGは検索・検証・アクセス制御・監査を統合した「知識ランタイム」へ進化中[^rag]。

## ④ MCPゲートウェイ

### 目的
エージェントが社内システム（GitHub、チケット、監視、Wiki、DB、ナレッジ基盤）に触る経路を1箇所に集約し、**認証・権限・監査・レート制御を一元管理**する。「エージェントは代行するユーザーと同一権限」の原則を技術的に担保する統制点。

### 構成

```
 Claude Code / Copilot / Genie / AI SRE / 自律ループ(⑦)
        │ (すべてのツール呼び出し)
        ▼
┌─────────────────────────────────────────┐
│ MCPゲートウェイ                            │
│ ・認証 (SSO連携、エージェント別クレデンシャル) │
│ ・認可 (利用者と同一権限にマッピング)          │
│ ・監査ログ (誰のエージェントが何を読み書きしたか)│
│ ・レート制限/コスト帰属 (→⑤へ送信)           │
│ ・MCPサーバーレジストリ (承認済みサーバー一覧)  │
└──┬───────┬───────┬───────┬───────┬──────┘
   ▼       ▼       ▼       ▼       ▼
 GitHub  チケット  監視/APM  Wiki   Databricks
```

- Phase 1 は承認済みMCPサーバーのリスト管理（レジストリ）だけで開始し、Phase 2 でゲートウェイ製品/OSSによる集中プロキシへ育てる。
- 野良MCPサーバーの接続禁止を L1 ルールに明記（サプライチェーンリスク対策）。

### 効果
| 指標 | 目安 | 根拠 |
|---|---|---|
| エージェントの社内データ事故 | 権限透過＋監査で構造的に防止 | エージェントガードレールの標準構成[^gw] |
| 新規ツール接続コスト | サーバー1本追加で全エージェントから利用可 | MCPの標準化効果（月間SDK DL 9,700万件）[^mcpsummit] |
| セキュリティレビュー | 個別ツールごと→ゲートウェイ1点に集約 | — |

> **事例注釈**: Uber は5,000人のエンジニア・1万超の社内サービスに対し MCPゲートウェイ＋レジストリを構築し、社内サービスのエンドポイントを自動的にMCPツール化。月間アクティブエージェント1,500、週6万回のエージェント実行を統制下で運用[^mcpsummit]。Block（Square）は社内エージェント goose の既定MCPサーバー（Snowflake・GitHub・Jira・Slack等）を整備し、全社でトークン消費98.7%削減を達成[^mcpsummit]。ゲートウェイは2026年のエンタープライズAIの「コントロールプレーン」と位置づけられている[^forbes]。

## ⑤ コスト・効果ダッシュボード

### 目的
従量課金時代（Copilot 2026/6〜、Claude Code、Databricks DBU）のコストを**チーム別・用途別に可視化**し、同じ画面で**効果（DX Core 4）と並べて見せる**。「使いすぎ」の統制ではなく「成果あたりコスト」の経営報告を可能にする。

### 構成（画面イメージ）

```
┌──────────────────────────────────────────────────────────┐
│ AI活用ダッシュボード (月次)                                  │
├────────────────────────────┬─────────────────────────────┤
│ 【コスト】                   │ 【効果 (DX Core 4)】           │
│ ・ツール別支出               │ ・変更リードタイム   ▼18%       │
│   Copilot ¥xx / Claude ¥xx │ ・デプロイ頻度      ▲1.4x      │
│   Databricks ¥xx           │ ・変更失敗率       →横ばい      │
│ ・チーム別支出 (10チーム)     │ ・節約時間       3.1h/週/人    │
│   ▂▅▃▇▂▁▃▅▆▃ +上限アラート │ ・AI起因不具合率  x.x%         │
│ ・成果あたりコスト            │ 【活用度】                     │
│   ¥xx/PR, ¥xx/障害対応      │ ・利用率 xx% / スキル利用 xx回  │
│                            │ ・ハーネス導入 xx/50システム     │
└────────────────────────────┴─────────────────────────────┘
```

### データソースと実装
| データ | 取得元 | 実装 |
|---|---|---|
| トークン/シート費用 | 各ベンダーAdmin API（Copilot、Anthropic、Databricks） | 横断集約はFinOpsツール or Databricks上に自作（データ基盤があるため自作も現実的） |

| 開発指標 | GitHub/CI/チケットのイベント | DX Core 4 準拠[^dora] |

### 効果
| 指標 | 目安 | 根拠 |
|---|---|---|
| コスト異常の検知 | 上限アラートで数日以内に検知（青天井の防止） | FinOps for AI標準プラクティス[^finops] |
| 経営への説明力 | 「効果あたりコスト」で投資継続判断が可能に | 検討項目B-3（2年目配賦移行）の前提データになる |
| 測定自体の効果 | 測定なしのAI導入は改善が停滞、が業界の結論 | DORA 2025[^dora] |

> **事例注釈**: FinOps Foundation が「FinOps for AI」ワーキンググループを設置し、トークン単位のコスト管理が標準化[^finops]。Datadog・Vantage 等はOpenAI/Anthropic/クラウドAIの支出を単一レポートに統合する機能を提供済み[^finops]。

## ⑥ AI SRE（運用工程のAI化）

### 目的
障害対応の「調査・整理・報告」をAIに移し、人間は**判断と意思決定**に集中する。50システム分の運用知識を③ナレッジ基盤と往復させ、対応するほど賢くなる仕組みにする。

### 構成（段階導入）

```
Step 1 (Phase 2 前半): 一次調査アシスト
  アラート発火 ─▶ 調査エージェント起動 (④経由で監視/ログ/デプロイ履歴/
  過去事例を横断) ─▶ 5分以内に「状況サマリ+原因仮説+類似事例」をチャネルに投稿
  ─▶ 人間が判断・対処

Step 2 (Phase 2 後半): 報告自動化
  対応ログから障害報告書ドラフト・タイムライン・再発防止案を自動生成
  ─▶ 人間がレビューして確定 ─▶ ③ナレッジ基盤に自動蓄積

Step 3 (Phase 3): リカバリ支援
  ランブック化された定型対処 (再起動、切り戻し、スケール変更) を
  人間承認付き (Human-in-the-Loop) でエージェントが実行
```

- 実装は「内製（Claude Code＋MCP＋監視連携）」と「製品（クラウドベンダーのSREエージェント等）」を Phase 1 末に比較評価（検討項目C-4）。内製は②④の資産を流用できるため初期候補。

### 効果
| 指標 | 目安 | 根拠 |
|---|---|---|
| MTTR | 30%削減（先進事例は30〜70%） | AI SRE導入企業の実績レンジ[^rootly] |
| 障害報告書の作成時間 | 80%削減 | ドラフト自動生成＋人間レビューの構成 |
| 深夜対応の負荷 | 一次調査の自動化でオンコール負担軽減 | AWS DevOps Agent / Azure SRE Agent が同構成でGA[^awssre] |

> **事例注釈**: AWS DevOps Agent と Azure SRE Agent は2026年3月にGAし、テレメトリ・コード・デプロイ履歴・リソース関係を横断分析する「一次調査エージェント」として提供[^awssre]。専業の Rootly 等はアラート発火と同時に調査を開始し数分で根本原因候補を提示するモデルを確立[^rootly]。

## ⑦ フロンティアウォッチループ

### 目的
「世の中が速すぎて個人では追いきれない」問題を、**組織の自律ループ**に転換する。最新動向の収集・評価・展開を仕組み化し、テンプレート（②）とマーケットプレイス（①）を常に最先端に保つ。部門初のループエンジニアリング実装（ドッグフーディング）。

### 構成（週次/月次サイクル）

```
┌── 週次 (自動) ──────────────────────────────────────────┐
│ 収集エージェント: リリースノート/論文/実践記事を巡回・要約     │
│   ─▶ 「今週の5件」レポート (影響度・当社関連度つき)           │
│   ─▶ CoEが15分レビュー: [試す] [見送る] [即展開] を判定      │
└──────────────────┬──────────────────────────────────────┘
                   ▼ [試す] 判定分
┌── 月次 (人+AI) ─────────────────────────────────────────┐
│ サンドボックスで検証 (評価用リポジトリ+評価シナリオを常備)      │
│   ─▶ 有効: ②テンプレート/①スキルを更新 ─▶ 全チームに自動配布  │
│   ─▶ 無効: 見送り理由を③ナレッジに記録 (再評価条件つき)       │
└─────────────────────────────────────────────────────────┘
┌── 四半期 ───────────────────────────────────────────────┐
│ ツールポートフォリオ再評価 (乗り換え/追加/廃止をCoEが判断)      │
└─────────────────────────────────────────────────────────┘
```

### 効果
| 指標 | 目安 | 根拠 |
|---|---|---|
| 最新プラクティスの導入リードタイム | 世の中の発表→全チーム展開まで数週間 | テンプレート自動配布（①②）との連動 |
| CoEリードの調査負担 | 週15分のレビューに圧縮 | 収集・一次評価をエージェント化 |
| 属人化リスク | 「追従できる個人」への依存を解消 | 判定基準・見送り理由がナレッジとして残る |

> **事例注釈**: ループエンジニアリング（Addy Osmani 提唱）の「スケジュール駆動で自律的に回り続けるループを設計する」考え方の適用[^loop]。観測データに基づきハーネス自体を自動進化させる研究（Agentic Harness Engineering）も2026年に登場しており[^harness]、このループは将来その受け皿になる。
