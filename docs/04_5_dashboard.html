コスト・効果ダッシュボード — 「成果あたりコスト」で語る

従量課金のAIコストと効果（DX Core 4）を同じ画面に並べる。KPIは「何を測るか」より「どう取るか」が難所 — 本ページは取得方法の実例を中心にまとめる。

1. 測定の設計原則 — 世の中の失敗から先に学ぶ

体感+20%
実測−19%
METR実験: 開発者の体感と実測は真逆になり得る
→ アンケート単独では測れない[1]
歪む
AIがコードの30〜70%を書くと、コミット数・行数・デプロイ頻度は指標として壊れる
Zylos Research 2026[2]
MTTR
AI時代に最も歪みにくいDORA指標（復旧は人の判断と運用に依存するため）
同上[2]
原則理由・実装
1. システム計測×サーベイのハイブリッド体感（サーベイ）と実測（Git/CI/API）を両方取り、乖離そのものを監視する。DX Core 4の標準手法[3]
2. 個人を測らない集計はチーム単位が最小粒度。個人ランキングは活用を萎縮させ、数字ゲームを生む（L1方針に明記）
3. 行数・コミット数を目標にしないAIで無限に増やせる指標は目標化した瞬間に無意味化する。参考値としてのみ保持
4. ベースラインを承認前に取るPhase 0で測定開始。「導入前後」が比較できないと効果は永遠に主張できない
5. 品質指標を必ず併走させる速度系だけ見ると品質劣化を見逃す（DORA 2025: AI比率+25ppで安定性−7.2%[1]）

2. 取得方法 — データソース別の実例

GitHub Copilot Metrics API（2026年2月GA）[4]

  • 取れるもの: アクティブユーザー、補完・チャット・coding agentの利用量、言語・IDE・モデル別内訳、AI Credits消費（2026年6月にpremium request制から移行）
  • チーム別集計: user-teamsレポート（2026年5月追加）でユーザー×チームを結合し、10チーム別の利用状況を出せる
  • 成熟度コホート: ai_adoption_phase フィールド（2026年5月追加）が直近28日の利用から各ユーザーの採用フェーズを自動分類 — 人材ラダー（L1/L2/L3）の進捗測定にそのまま使える
  • 実装: REST APIを日次で取得→Databricksに蓄積。公式の可視化OSS（copilot-metrics-viewer）も参考に

Claude Code — 管理ダッシュボード ＋ OpenTelemetry ＋ Analytics API[5]

  • 管理ダッシュボード（2026年7月拡充）: 週次アクティブ利用者、PR数、受け入れ行数、スキル採用率、コミット当たりコスト、月次・四半期の支出を組織単位で表示。⑤の自作範囲は「ツール横断の統合」に絞れる
  • OTelエクスポート（公式サポート）: トークン消費・推定コスト・ツール実行・セッション情報をOTLPで送信。環境変数を managed settings（②）で全端末に配布すれば計測は自動化される
  • 送信先: OTLPコレクタ→Databricks（自作）または Grafana/SigNoz 等。Elastic等でのSIEM連携事例もあり（D-5の監査要件と両取り）
  • Analytics API: Team/Enterpriseプランは利用状況・エンゲージメント指標をAPIで取得可能
  • スキル利用の計測: ツール実行イベントから①のスキル呼び出し回数・利用チームを集計
# managed settingsで配布する計測設定（例）
CLAUDE_CODE_ENABLE_TELEMETRY=1
OTEL_METRICS_EXPORTER=otlp
OTEL_EXPORTER_OTLP_ENDPOINT=https://otel-collector.internal:4317
OTEL_RESOURCE_ATTRIBUTES=team=payment,dept=dx   # チーム帰属タグ

AWS／Databricks側のコスト

  • Bedrock: モデル呼び出しログ＋Cost Explorer（タグ: チーム／用途）。自律ループやAI SREのコストはここに乗る
  • AgentCore Observability（④のAPI・Lambda系統制）: エージェント実行単位のログ→「¥/障害調査」「¥/自律ループ実行」の分母に
  • Databricks: system tables（billing.usage）でDBU消費をワークロード別に集計 — ③⑤の運用コスト
  • Unity AI Gateway（⑧経由の利用）: 組み込み利用ダッシュボードが標準装備 — リクエスト・トークン・コスト内訳・外部MCPトラフィックをチーム/用途タグ別に表示。system.ai_gateway.usageで自由分析。⑤はこれを土台に拡張すればよく、D-4の自作コストを大きく下げる
  • 横断集約: FinOps for AIの標準手法。Vantage等はOpenAI/Anthropic/AWSの請求を単一レポートに統合するが、当社はDatabricks上の自作が第一候補（D-4）[6]

開発活動 — DORA系メトリクス（GitHub／CI）

  • 変更リードタイム: first commit→本番デプロイ（GitHub API＋デプロイイベント）
  • 変更失敗率／MTTR: デプロイ×インシデント管理の紐付け（⑥の記録と連動）。MTTRはAI時代に最も信頼できる指標[2]
  • AI起因の切り分け: AI関与PRのラベリング（coding agent起票・Claude Codeのco-author署名で自動判定）→ AI関与PRと非関与PRの品質・サイクルタイム比較（AI Usage Diff Mapping[2]）が「AIは効いているか」への最も直接的な回答になる
  • レビュー負荷: PRあたりレビューコメント数・レビュー滞留時間

サーベイ（体感）— 四半期・5分・チーム単位

  • 設問例: 週あたり節約時間（自己申告）／AI出力への信頼度／摩擦を感じる場面（自由記述）
  • 実例: 120人中80人にCopilotを配布した企業がDX Core 4で2ヶ月計測 — 満足度+9pt、自己申告の節約2.4時間/週/人（月768時間）をシステム指標と併記して報告[3]
  • METR対策: 自己申告の節約時間は実測リードタイムと並べて表示し、乖離が大きいチームは深掘り（体感だけで投資判断しない）[1]
  • 回収率の担保: CoP内で結果を必ずフィードバック（「答えると改善される」体験を作る）

5. 事例と落とし穴

事例 Copilot Metrics APIは2026年に急速に整備（2月GA→5月チーム別・adoption_phase→6-7月精度改善）[4]。 Claude CodeのOTel計測はGrafana/SigNoz/Elastic等での構築例が多数公開[5]。 DX Core 4での2ヶ月計測例（80/120人、2.4h/週）[3]。パナソニック コネクトは全社AIで年18.6万時間削減を「時間」で報告 — 経営に通じる単位の好例[7]。
落とし穴（反面教師） 利用率だけの報告（「84%が使うが信頼は33%」が世の中の実態[1] — 利用率が高くても成果ゼロはあり得る）／ 体感アンケート単独（METRの体感+20%/実測−19%）／ 個人監視化（数字ゲームと萎縮を生む。チーム集計を最小粒度に）／ 測定システムの作り込みすぎ（Phase 0は「Copilot API＋スプレッドシート」でも始まる。完璧を待たない）。
