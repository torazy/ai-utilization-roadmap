フロンティアウォッチループ — 「追いつく」の仕組み化

最新動向の収集・評価・展開を自律ループにする。「世の中が速すぎて個人では追いきれない」を、週15分の判定業務に変える。部門初のループエンジニアリング実装。

1. 何を解決するか

活用パラダイムは数ヶ月単位で更新される（ハーネス→ループ、coding agent GA、AgentCore登場…すべてこの1年の出来事）。 現状は追従できる個人（フロントランナー）に依存しており、その個人でさえ「追いきれない」と感じている。 これは根性の問題ではなく構造の問題 — 収集と一次評価を機械化し、人間は判定だけに絞る。

属人
最新知識が特定個人に依存。休暇・異動で部門の目が止まる
週15分
仕組み化後にAI推進チームが使う判定時間
数週間
世の中の発表 → 全チームのテンプレ反映までのリードタイム

2. ループの構成

収集（週次・自動）公式changelog・ブログRSS・arXiv・実践記事を巡回エージェントが要約
→
スコアリング（自動）影響度×当社関連度で採点し「今週の5件」を絞り込み
→
判定（人・15分）AI推進チームが 試す／見送る／即展開 を判定（下記ルーブリック）
→
検証（月次）評価用サンドボックスで実測 — 評価リポジトリ＋評価シナリオ＝社内ミニベンチマーク
→
展開（自動）有効ならテンプレ（②）・スキル（①）を更新PR → 全チームに同期
→
記録見送り理由と再評価条件を③に記録（同じ議論を繰り返さない）

2-1. 情報源リスト（初期セット）

カテゴリソース例頻度
利用ツールの公式Claude Code changelog／GitHub Copilot changelog／AWS What's New（Bedrock・AgentCore）／Databricksリリースノート週次
実践知DORA・DXブログ、主要テックブログ、国内実践記事（Findy等）週次
研究arXiv（agent／SWE系。要約のみ）週次
規制・ガバナンスAI事業者ガイドライン改訂、EU AI Act動向月次

ソースは厳選20本以内を維持（多いほどノイズが増え判定が形骸化する）。四半期で入れ替え。

2-2. 判定ルーブリック（属人化させない）

判定基準その後
即展開リスクなしの改善（例: ツールの設定改善、コスト削減設定）テンプレ更新PRを当週内に配布
試す効果が大きそうだが検証が必要（例: 新しいエージェント機能、新モデル）翌月のサンドボックス検証へ。検証観点を明記
見送る当社前提に合わない／成熟待ち／可搬性が低い（特定ツール深依存）理由と再評価条件（例: GA後・事例3件以上）を③に記録

2-3. サンドボックス検証（社内ミニベンチマーク）

  • 評価リポジトリ: 当社の典型コード（レガシー含む）を模した検証用リポジトリ2〜3本
  • 評価シナリオ: 定型タスク10本（バグ修正・機能追加・文書生成・調査）— スキル昇格時の「正解サンプル」（①）を流用
  • 測るもの: 成功率・所要時間・トークンコスト・出力品質（Checkerエージェントが採点）
  • これにより「新しいツール/手法が当社で効くか」を感想ではなく数字で判定できる

3. 運用と実装

実装
収集エージェント＝スケジュール実行（cron）のClaude Code／Agent。要約→スコア→チャネル投稿まで無人。これ自体が自律ループの練習台（停止条件・コスト上限を実装してループ詳説の型を検証する）
週次金曜 15分
AI推進チーム全員で判定（リードだけに依存させない — 複数名運営が属人化対策）
月次
サンドボックス検証（1〜3件）。結果をCoPで共有し、テンプレ更新の背景を現場に説明
四半期
ツールポートフォリオ再評価（乗り換え・追加・廃止の判断）。情報源リストの入れ替え

4. KPIと計測方法

指標取得方法目安
評価件数／採用率判定記録（③）の集計週5件評価・採用率2〜3割
展開リードタイム世の中の発表日→テンプレ配布日即展開1週間・検証経由6週間
判定の複数名化判定参加者数（属人化の監視）常時3名以上
ループ自体のコスト⑤で計測（収集・検証のトークン費）上限額を設定

5. 落とし穴

落とし穴（反面教師） ノイズ過多（ソースを増やすほど「今週の5件」の質が落ちる。厳選リストを守る）／ 判定の形骸化（全部「試す」にすると検証が詰まる。月の検証枠は3件まで）／ 新しもの好きの暴走（可搬性原則 — スキル/MCP/AGENTS.mdに乗らない深依存は原則見送り）／ 見送り記録の省略（記録がないと同じ議論を毎月繰り返す）。
