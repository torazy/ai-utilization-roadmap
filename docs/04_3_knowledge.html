ナレッジ基盤 — 蓄積もAI・活用もAI

障害対応・設計判断・レビュー知見を、発生した瞬間にAIが構造化して蓄積し、次のAI実行のコンテキストとして自動供給する。人がナレッジを「書く」「探す」をやめる。

1. 何を解決するか

消える
障害対応の知見がチャットログと個人の記憶に埋没
50システム
暗黙知が有識者個人に集中。異動・退職で保守不能リスク
0
AIリバース文書化による工数削減の先行事例
富士通 2026/3 SaaS[1]
設計原則 「人にナレッジを書かせる」施策は歴史的に失敗してきた。本基盤は人の追加作業ゼロを原則とする — 蓄積はイベント駆動でAIが行い、活用はエージェントが検索する。人は「確定レビュー」だけ。

2. アーキテクチャ — 蓄積と活用の2つの面

発生障害対応チャネル／PRマージ／ADR追加／定例議事録
→
収集Webhook・イベントで収集エージェント起動（人は何もしない）
→
構造化要約・タグ付け・関連付け。定型スキーマに変換（下記）
→
確定作成者が2分でレビュー（Slackのボタン承認）→ 格納
→
活用開発エージェント／AI SRE／Genieが④経由で検索・参照
→
鮮度維持コードとの差分を夜間検出→更新PR自動起票（Phase 3）

2-1. 置き場の設計（フェデレーション構成 — 検討項目A-3）

ナレッジ種別ソースオブトゥルース理由
設計文書・ADR・規約各リポジトリ docs/（Git管理）コードと同じレビューフロー・同じPRで更新。ハーネス（②）から直接参照
障害記録・ポストモーテムDatabricks（Deltaテーブル＋Vector Search）システム横断で検索される。AI SRE（⑥）の主参照先
横断ナレッジ（用語・業務知識・判断集）Databricks（Genie Ontology[2]）業務エージェントと共用。自己改善するコンテキスト層
検索の入口どちらも④MCPゲートウェイ経由の検索ツール1本に統合 — 利用者と同一権限で横断検索

2-2. 構造化スキーマ（障害ナレッジの例）

# incident-knowledge スキーマ（収集エージェントが自動生成 → 担当が2分レビュー）
id: INC-2026-0142
system: payment-batch          # 50システムのカタログIDに紐付け
symptom: "夜間バッチが02:00頃タイムアウト"
root_cause: "結線プールの枯渇（先月の設定変更 #PR-881 が誘因）"
detection: CloudWatch alarm → 調査エージェントが類似事例 INC-2025-089 を提示
resolution: "プールサイズ復元＋リトライ設定追加"
prevention: "設定変更PRにレビュー観点『接続数影響』を追加（→①スキル更新済み）"
links: [PR-881, runbook/payment-batch.md]
embedding: 自動付与（Vector Search同期）

肝は prevention がスキル（①）やハーネス（②）の更新に接続されること — ナレッジが「読む物」でなく「仕組みの改善」に変わる。

2-3. 検索の技術構成

層実装
ハイブリッド検索Databricks Vector Search（ベクトル）＋ キーワード（BM25）。純ベクトルは専門領域で15〜20%外すため必須[3]
リランカー上位候補をLLMで再順位付け（Agent Bricksの文書検索サブエージェント活用[2]）
アクセス制御Unity Catalogの行・列レベル権限。エージェントは代行するユーザーと同一権限（④のIdentityで担保）
監査誰の（どのエージェントの）検索が何を参照したかをログ（→⑤・D-5）

3. 運用

Phase 1
コード系から開始: legacy-docスキル（①）で優先3〜5システムの設計書をリバース生成し docs/design/ に格納。障害記録の構造化テンプレを手動運用で試行
Phase 2
収集エージェント稼働（障害チャネル・PR・ADRのWebhook連携）。Databricks側にVector Search索引、④経由の検索ツール公開
Phase 3
鮮度ループ（夜間差分検出→更新PR）稼働。Genie Ontologyと接続し業務側と相互参照
月次
品質サンプリング: ランダム10件を有識者が採点（誤り・古さ）。低品質ソースは収集対象から外す
運用の分担（Databricks運用チームと） 索引・テーブル・権限の管理はDatabricks運用チーム、収集エージェントとスキーマはAI推進チーム、内容の正しさは各チーム（確定レビュー）— 三者の役割を検討項目Aの協議で確定する。

4. KPIと計測方法

指標取得方法目安
設計書カバレッジ50システム中、docs/design/整備済みの数（②の認定と連動）10→25→50
ナレッジ参照率エージェント実行のうちナレッジ検索ツールを使った割合（④のログ）障害調査で80%+
類似事例ヒット率障害対応時に過去事例が提示され「役立った」とマークされた率（⑥のフィードバックボタン）50%+
鮮度設計書の最終更新からの日数分布／コード差分検出の未解消数90日以内90%

5. 事例と落とし穴

事例 富士通: コード→設計書の自動生成SaaSで工数97%削減[1]。 Databricks Genie Ontology: 組織ナレッジの自己改善コンテキスト層＋Lakebaseエージェントメモリ[2]。 エンタープライズRAGは検索・検証・権限・監査を統合した「知識ランタイム」へ[3]。
落とし穴（反面教師） ゴミの自動蓄積（構造化の品質ゲートなしに溜めると検索が汚染される → 2分確定レビューと月次サンプリングを外さない）／ 権限の平坦化（「全部見えるRAG」は情報漏洩装置になる。Unity Catalog権限の透過を最初から）／ ベクトル検索単独（専門用語・型番・エラーコードで外す → ハイブリッド必須[3]）／ 「書く文化」への逆戻り（人手入力の項目を増やした瞬間に止まる。入力はAI、人は承認のみ）。
